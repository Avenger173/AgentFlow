# C6 总指挥组合调度与会话连续性计划

最后更新：2026-08-26

## 当前状态

**C6.5.4 客户表达与直接只读问答已完成，C6 当前已批准范围已收尾。**历史任务会如实展示文档、数据和知识库子任务实际保存的脱敏 Route/provider/model/thinking 与调用阶段；调度台主对话不再把计划、事件与日志当作客户回答。该项没有新增 Agent 或客户可购买功能，没有调用模型、读取客户材料或改写旧任务。下一项必须先回到客户价值、输入输出和验收讨论，不能因为 C6 平台能力已齐就自行扩张新的 Agent 范围。

## 背景与问题

客户在 AI 调度台绑定资料库后，当前确定性计划能正确生成 `knowledge_agent.answer_question`，但独立生成的首段模型回复仍可能声称“不能访问资料库”。同时调度台只有视觉上的聊天记录：每次请求只携带当前消息，缺少会话 ID、自动上下文压缩和组合材料选择。后端启动期间若直接提交聊天请求，客户端会等待不可用服务的网络超时，造成“卡住且不知道是否收到”的体验。

这不是知识库回答能力本身失败，而是总指挥的会话、计划表达与执行编排尚未成为同一条可信链路。

## 当前实现状态

- **C6.1 已完成：**Commander 现在先生成并校验结构化计划，再把脱敏计划事实交给表达模型。若模型仍明确否认已绑定且已准入的材料，服务端会退回可审计的计划说明；资料库 dry-run 不再出现“无法访问”与 `knowledge_agent.answer_question` 同时成立的冲突。Qt 在后端未 ready 时只暂存一条已冻结材料范围的请求，ready 后自动发送；启动失败则还原输入，而不是等待 HTTP 超时。
- **C6.2 已完成：**`conversation_id` 自动创建并回传，SQLite 保存会话标题、当前材料引用、最近 task/plan 指针和最多 1400 字的确定性早期摘要。消息以微秒时间和同轮有序 ID 保存，保证“用户 -> 助手”的恢复顺序。客户第一轮明确选择材料后，后续只有出现“刚才/上一步/这份资料”等明确指代时才会复用该会话材料；新会话或切换 `project_scope` 都不会继承旧范围。Qt 会连续显示同一会话消息，重启后从只读恢复接口重新展示早期摘要和近轮记录，并提供“新建对话”图标；它只切断短期会话，不删除任务历史或长期记忆。
- **C6.2.5 已完成：**会话改为“完整受控归档 + 有界模型上下文”。客户可切换同一范围内的最近会话，并按页查看完整脱敏记录；已保存的聊天正文不再因超过近轮窗口而删除。模型每轮仍只取得摘要、最近有限消息与明确材料，避免把“完整历史可见”误实现为无限 Prompt。早期已被旧版本压缩删除的正文无法凭空恢复，但新版本之后不会继续删除。
- **C6.5.4 已完成：**单资料库、无写入/联网/确认、且只委派 `knowledge_agent.answer_question` 的请求会在 dry-run 后自动进入安全 Runtime。聊天区只显示“正在检索”与 K3 Evidence Gate 已验证的最终回答及精简来源；计划、Node Contract、事件流、预算和完整日志仍只在“查看计划”与任务历史中按需查看。最终回答以关联 K3 子任务 ID 幂等追加到同一会话归档，重启恢复时按 Markdown 重新排版；会话正文仍受既有脱敏和长度边界约束，完整长回答与全部来源以任务历史为准。
- **C6.3 已完成：**AI 调度台把从文档、数据工作台和知识库带入的受控材料显示为可单独移除的标签，三类材料可在同一轮显式绑定，不再由页面跳转相互清空。Commander 会让无数据依赖的只读专业步骤共同依赖任务分析节点、标记同一并行组，并追加“等待专业结果后汇总”的 DAG 节点。
- **C6.4 已完成核心闭环：**Native Runtime 已实际调度 `document_agent.analyze_document`、`document_agent.search_text`、`data_agent.analyze_dataset`、`knowledge_agent.answer_question` 四类白名单只读动作。每轮最多两个执行槽位、最多三条专业分支，启动前预留父任务 Tool 预算；各子任务仍保留自己的历史、来源和验证。一个分支失败不会取消其它独立分支，父任务只汇总已完成子任务的脱敏摘要，并明确标记“部分完成”。旧计划或包含深度分析、导出、OCR、联网、写入等动作的组合仍保持 `requires_composition_runtime`，不会被抢跑。
- **启动测量：**隔离目录中的后端冷启动测量为模块导入约 `2714ms`、lifespan 恢复约 `124ms`、首次 `/health` 约 `4ms`。当前主要成本是已稳定路由的 Python 导入，不是 SQLite 恢复；本轮先解决提交卡死，后续若继续缩短首启必须以该基线和真实客户数据复测，不能跳过检查点恢复来换取假速度。

## C6 产品目标

让客户以一段自然语言提出任务后，总指挥能够：

1. 基于已登记且可执行的 Agent action，明确说明本次可完成、不能完成、还需选择材料或确认的部分。
2. 对客户主动选择的文档、一个数据集和一个资料库生成可审阅计划；不因一句模糊指令扫描本机材料。
3. 按真实依赖串行或并行委派专业 Agent，并在父任务中汇总真实子任务状态与经过边界压缩的结果。
4. 自动保持同一调度会话的短期上下文，长对话以摘要替代无界全文重传。
5. 在后端尚未就绪时安全暂存一次提交并清楚反馈，服务 ready 后自动发送，不制造 HTTP 超时假卡死。

## 记忆分层

### 自动会话记忆

- AI 调度台为每个新会话生成稳定 `conversation_id`；它是自动开启的基础交互能力，不需要客户逐条点击“记住”。
- SQLite 保存会话标题、完整的脱敏聊天归档、已确认材料引用、当前计划/Runtime 指针和受控摘要；不保存 API Key、绝对路径、原始文件全文、原始表格行或模型隐藏推理。
- 模型上下文只取得“短摘要 + 最近有限轮消息 + 本轮明确材料/计划事实”。超过预算时在后台以结构化摘要替代早期对话；归档正文供客户按页查看和切换，不会被整段重新塞入模型。
- 新建会话、切换会话、清空当前会话和会话摘要的范围必须在 UI 可见；会话关闭不等同删除历史任务。会话档案与跨会话长期偏好严格分层。

### 跨会话长期记忆

- 继续只保存用户可查看、编辑、关闭和删除的偏好、项目约束、已验证经验。
- 自动会话记忆不得暗中升级为永久个人画像。现有“记住约束”保留为低频确认入口，后续可优化成任务结束时的清晰建议，不以逐句确认打断对话。

## 编排与多次模型调用

- 一次客户任务可以包含多个模型回合，但不是为了堆调用次数：规划/能力说明、专业 Agent 的受限 Tool loop、以及最后的结果汇总各自有明确责任。
- 专业 Agent 的既有 Runner 上限继续生效；组合任务另设总模型回合、并发、耗时和成本预算。超出预算应停在可恢复状态并说明未完成范围。
- 仅没有数据依赖、无写入冲突、无共享限额冲突的只读子任务才可并行。并发许可和预算必须在启动前原子预留，不能等分支结束后再累计。
- 写入、导出、联网、OCR 准备和深度分析仍按各 Agent 的独立确认/权限规则运行，不能因“总指挥组合任务”绕过。
- 当前能力目录必须成为唯一事实源：`enabled && runtime_ready && health=ready` 才能写进可执行步骤。代码工坊、报告助手等占位能力必须明确列为不可用，不能被模型许诺。

## 计划与回复一致性

1. 先由确定性 Commander 生成并校验计划，再把脱敏的能力、材料、步骤、限制和当前阶段传给表达模型。
2. dry-run 阶段的回复只能说明“已规划/待确认/尚未读取”，绝不能声称已经拿到专业结果，也不能否认已被计划准入的材料或能力。
3. Runtime 后由父任务汇总器基于真实子任务输出产生最终答复；没有完成的子任务必须标注状态、范围和恢复入口。
4. “能力说明”是一个正式的无副作用计划类型：对用户目标列出可调用能力、材料前置、不可用动作和预计交付，不伪造委派或产物。

## 组合材料与 UI

- AI 调度台提供渐进披露的“本次材料”区，分别显示已选文档、数据集、资料库；每类材料可单独移除，默认不显示文件绝对路径。
- 客户可选择 0-1 份数据集、0-1 座资料库和受控文档集合。组合前必须显示读取范围与“不会做什么”。
- 主工作区只保留对话、当前状态和一个主要操作；计划、能力矩阵、子任务依赖图和长结果放入可展开 Inspector/详情页，避免把控制台堆成密集表单。
- 所有提交都应在 50-100ms 内进入“已暂存/已规划/执行中/等待确认/完成/失败”之一；运行指示器必须由真实状态驱动，终态立即停止。
- 对话主区只显示自然语言结论、当前计划一句摘要和下一步；工具参数、Node Contract、原始日志、完整步骤表、预算细项和修订表单只在“查看计划”或历史 Inspector 按需展示。
- “查看计划”使用独立的阅读与修改区域，任何窄窗口下都不能让版本表、计划正文和修改控件互相遮挡。

## 实施顺序与验收

### C6.1 启动与计划表达一致性（已完成）

- 后端未 ready 时，Qt 暂存一条待发送任务，保留输入材料，ready 后自动提交；后端失败时恢复输入并给出重试提示。
- `create_llm_chat_response` 先创建 Commander plan，再以其脱敏摘要约束模型回复。
- 回归：`verify_commander_c6_planning.py` 覆盖“模型错误宣称无法访问 -> 服务端安全计划说明”；绑定资料库的 dry-run 必须明确“已规划，点击开始执行后由知识库子任务读取”。Qt Creator Debug 构建和 `verify_backend.py` 已通过。

### C6.2 自动会话上下文（已完成）

- 新增 SQLite 会话/消息摘要协议、`conversation_id` API、只读恢复接口与 Qt 会话生命周期。Qt 重启后恢复早期摘要和有限近轮记录，不保存聊天正文到 QSettings。
- 回归：`verify_commander_c6_conversation.py` 覆盖首轮材料绑定、用户/助手消息时序、连续指代复用、8 条近轮上限后的摘要、重启恢复接口、不存在会话不隐式创建、新会话隔离与 `project_scope` 隔离；不会跨会话读取旧正文或材料。当前摘要为不额外消耗模型额度的确定性压缩，后续只在确有质量问题时评估受控模型摘要。

### C6.2.5 会话归档与切换（已完成）

- 保存全部已脱敏的用户/助手消息；Prompt 读取仍固定为“摘要 + 最近有限消息”，不能以“无限记忆”为由无界消耗上下文和模型额度。
- 新增会话列表与分页正文读取接口。Qt 仅把不透明 `conversation_id` 存入 `QSettings`，正文由后端按需读取；切换会话后显示该会话摘要和最近记录，并可打开完整记录。
- 回归：超过 8 条消息后，数据库归档数仍递增；Prompt 快照仍不超过上限；会话列表和分页正文不会跨 `project_scope` 返回记录。

### C6.5 显式模型路由（进行中，C6.5.1-C6.5.2 已完成）

- 建立客户可见的模型路由 Profile：总指挥规划、总指挥汇总、文档分析/PPT、数据洞察、知识库问答/深度分析、视觉生成等作用域均可选择“继承全局”或明确 provider、模型与思考模式。
- Key 仍只由既有安全存储管理。Profile 只能选择已经配置且能力满足 JSON、工具、视觉等要求的模型；不兼容时明确提示，绝不静默换到其它模型。
- 每个任务/子任务保存脱敏的 provider、model、thinking、profile 与实际兼容性降级说明，便于客户判断实际使用了什么，而不回显密钥。
- **C6.5.1 已完成**：后端新增 `model_route_profiles.json` 原子仓储和 `/api/models/routes` 读写接口；路由配置只保存作用域、provider、Base URL、模型与思考模式，API Key 继续复用原有 Provider 级 DPAPI 安全存储。保存前会校验 Key、思考模式及 JSON/Tool Calls 能力；视觉生成因尚未接入通用图像模型目录而保持 `reserved`，不能伪装为可执行。
- 总指挥规划已成为首个真实路由入口，并把脱敏 `model_route` 快照写入聊天响应和 dry-run `WorkflowRun`。文档分析、PPT、数据洞察、知识库问答和深度任务的默认解析也已改为各自作用域。
- **C6.5.2 已完成**：模型页提供独立的“任务模型路由”检查器，左侧定位作用域、右侧渐进披露当前一项配置；它不复制 API Key、不触发模型调用，也不挤压全局 Provider 配置。PPT 主计划、数据草稿和联网抽取已移除跨 Provider 的隐式 DeepSeek 回退：选定模型失败时只返回真实原因或本地确定性草案，客户必须显式修改 `document_presentation` 路由后再重试。
- **C6.5.3 已完成**：文档分析、数据洞察、知识库问答与知识库深度任务会把实际 Route Runtime 的脱敏快照写入同一 `WorkflowRun.model_routes`；深度任务会分别记录 `knowledge_deep_map` 与 `knowledge_deep_reduce`，从而允许同一次运行按阶段展示不同模型。确定性 Tool、mock 或旧版本没有快照时保持为空，不以当前全局配置补猜。
- 历史页使用独立只读 `GET /api/tasks/{task_id}/model-routes` 按需读取。任务标题行只有确实有快照时才显示紧凑图标，点击后显示阶段、Route、Profile、Provider、模型与思考状态；正文只保留一行摘要。旧任务明确提示“历史版本未记录实际模型路由”，不会挤占权限、产物或结果阅读区域。
- 回归：`backend/scripts/verify_model_routes_c65.py` 用 fake 模型验证继承/显式 Profile、思考能力拒绝、视觉保留态、Commander 实际解析和任务快照；新增 `backend/scripts/verify_model_route_audit_c653.py` 以临时 SQLite 覆盖单阶段、多阶段多模型、旧快照缺失及 Key/Base URL 脱敏。两者均不联网、不读取客户资料、不写入真实配置或 API Key。

#### C6.5.3 专业子任务模型审计（已完成，平台收尾）

- 目标：让历史任务中的文档、数据、知识库子任务展示本次实际解析到的脱敏 provider、model、thinking、route ID 与执行阶段；同一任务若使用多个模型，必须按阶段列出，不能汇总成一个猜测值。
- 边界：只读取任务已记录的脱敏快照和事件，不回显 API Key、原始 Provider 响应、材料正文或账户信息；旧任务缺失快照时明确显示“该历史版本未记录”，不伪造数据。
- 不做：不新增模型页表单、不改变客户已保存的 Route、不触发模型调用、不改写既有任务、不把此审计项包装成新的专业 Agent。
- 验收：离线夹具已覆盖单模型子任务、多阶段多模型、缺失旧快照和 Key 脱敏；Qt 历史 Inspector 只在实际有审计数据时显示紧凑摘要，完整详情按需展开，且新增入口位于既有标题行，不改变现有产物与权限区布局。Qt Creator Debug 构建已通过；客户本机可在下一次真实文档、数据或知识库任务完成后，从“历史任务”验证该只读入口。

#### C6.5.4 客户表达与直接只读问答（已完成）

- 目标：让“请根据资料库回答……”像正常聊天产品一样交付结论，而不是要求客户阅读 dry-run、节点契约、事件流或 Runtime ID。
- 准入：服务端与 Qt 同时核验 `ready`、无写路径、无外部服务、无确认、仅一个 `knowledge_agent.answer_question` 专业步骤及有效资料库 ID；任一条件不满足时，仍遵循原有计划审阅和权限流程。
- 交付顺序：客户问题 → 一句真实检索状态 → K3 已验证回答与最多四条精简来源。原始日志、Tool 参数、产物卡、复盘指标和完整来源始终留在历史/Inspector，不再灌入对话正文。
- 会话：规划阶段保存简短状态，不保存表达模型的长篇计划；Runtime 完成后只从关联 K3 子任务读取 Evidence Gate 已验证正文，以稳定子任务 ID 幂等追加助手交付。恢复会话时保留 Markdown 层级；归档仍脱敏、限长，完整任务结果不被复制或替代。
- 验收：`verify_commander_c6_planning.py` 覆盖冲突规划回复的收束、短状态归档与异步最终交付幂等；`verify_knowledge_answer.py`、`verify_commander_c64_runtime.py`、全量后端回归与 Qt Creator Debug 构建共同覆盖 K3/C6 既有边界。

### C6.6 `@` 能力约束（已完成，依赖 C6.3-C6.4）

- `@文档助手`、`@数据工作台`、`@知识库` 是客户对本轮路由的显式偏好和材料提醒，不是权限提升、MCP 自动加载或绕过 action 准入。
- 支持多个目标时，UI 必须把解析出的 Agent 与材料显示为可移除标签；缺少所需材料时先澄清。只有 C6.4 的真实组合 Runtime 完成后，多个目标才会并行或串行执行并由总指挥汇总。
- **已完成**：调度台输入框旁增加受控 `@` 菜单，且输入中的中英文有限别名会同步显示为可移除的“路由”标签。客户端只提交三项已实现 Agent ID；后端仍从消息文本二次规范化，不能把 Qt 状态当作唯一可信来源。
- **已完成**：`WorkflowPlan.agent_hints` 会写入计划、版本和会话快照。只要客户点名其中一项，计划会过滤掉其它未点名类型的材料，缺失对应材料时只返回澄清问题，不扫描本机目录、不猜测资料库或数据文件。
- **已完成**：点名多个已绑定的只读能力时，继续复用 C6.4 的并行/汇总白名单；深度分析、OCR、导出、联网、写入和未知动作仍不可借 `@` 进入 Runtime。计划摘要会显示实际的本轮路由，表达模型也只能解释这份已校验快照。
- 回归：`backend/scripts/verify_commander_c66_agent_hints.py` 覆盖单点名的材料收束、缺材料澄清、三项组合和未知 Agent API 拒绝；不读取客户文件、不调用模型或网络。

### C6.3 组合计划与依赖图（已完成）

- AI 调度台新增“本次材料”可见标签：文档、数据集、资料库可同时存在，并可在发送前单独移除；标签仅展示受控名称，不展示绝对路径、正文或数据行。页面之间只添加当前客户选择，不会再暗中清空其它已显示材料；发送、暂存、新建/切换会话后统一清空或恢复可见状态。
- `WorkflowStep` 新增 `parallel_group`，`WorkflowPlan` 新增 `execution_readiness`。多个只读专业步骤共同依赖 `step_1` 并归入 `specialist_read_only`，最后的 `commander_agent.synthesize_results` 表达汇总依赖与结果范围。
- `requires_composition_runtime` 继续是服务端强制保护，但只针对尚未进入 C6.4 白名单的组合。已支持的文档/数据/知识库只读组合会生成 `ready` 计划；Qt 可正常进入真实 Runtime。
- 回归：`backend/scripts/verify_commander_c63_composition.py` 覆盖文档 + 数据集 + 资料库组合的显式材料、DAG、并行组、汇总节点与 dry-run 协议；不读取客户文件、不调用模型或网络。

### C6.4 真实执行与汇总（已完成核心闭环）

- Native Runtime 在 `step_1` 的无副作用计划消费完成后，按 `specialist_read_only` 组启动专业子任务；每组最多两个线程，最多三条专业分支。父 Runtime 在启动线程池前原子预留父级 Tool 预算 `12`、任务时间预算 `240s`，并在每个分支终态后以 append-only 事件和 SQLite checkpoint 保存事实。
- 分支仅限已验证的只读入口；子任务自行拥有模型调用、来源、失败和 artifact 历史。父任务只保存关联 `delegated_task_id`、短结论、来源/图表计数与状态，不复制原文、数据行、证据片段或模型 Prompt。
- 汇总器当前是确定性控制节点，不再额外消耗模型额度；它只接收 `completed` 子任务的脱敏摘要。若存在失败/阻塞分支，父任务仍可 `completed`，但摘要和 `completion_state=partial` 会明确未完成范围；若没有任何完成分支，则停在可解释的 `blocked/failed` 状态。
- 已有暂停、取消和权限检查点继续沿用 Native Runtime 的安全边界：已完成步骤不会重跑；正在运行的子任务不会被强杀，当前批次返回后才消费暂停/取消。深度任务因其独立后台状态机不在本轮即时汇总范围。
- 回归：`backend/scripts/verify_commander_c64_runtime.py` 以脱敏 fixture 覆盖三条专业分支、两个并发槽位、单分支失败隔离、部分完成结果范围、父级预算与 append-only 事件；`verify_commander_c63_composition.py`、`verify_backend.py` 和 Python 编译检查均通过。下一阶段仍需客户用真实选中的材料做一次 Qt 端到端验收，不能把 fixture 通过写成所有专业组合都已现场验收。

DeepSeek Harness 继续是可选 `ExecutionBackend`。C6 先以 Native Runtime 验证组合调度语义；只有出现需要它的长周期恢复场景时，再按既有 H2 门槛引入，不替换 AgentFlow 的权限、审计与产物所有权。
