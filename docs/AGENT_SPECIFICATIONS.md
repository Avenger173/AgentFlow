# AgentFlow 内置 Agent 方案确认

最后更新：2026-07-31

本文档用于在正式实现每个 Agent 前先确认产品边界。Agent 可以协作，工具可以共用，但每个 Agent 的职责、权限、定价属性和验收标准必须独立讨论。

## 确认流程

1. 每次只讨论一个 Agent。
2. 先写清楚该 Agent 的职责、用户价值、明确不做什么、可调用工具、权限边界和验收标准。
3. 用户明确同意后，才进入功能实现。
4. 实现中如果发现边界需要变化，先回到本文档更新方案，再继续写代码。
5. 临时 mock、演示字段、测试按钮不能自动升级为正式 Agent 能力。

## 产品功能立项门槛

2026-07-31 已确认：后续所有 Agent 都按“解决真实任务并交付可使用结果”来设计，功能在精不在多。摘要、问答、改写、提取、提纲等通用 LLM 能力不能仅因做成按钮或输出模式，就被视为有竞争力的一级产品功能；它们应优先作为完整工作流中的内部步骤、Tool、配方或验证材料。

每个新 Agent 或一级功能进入实现前，必须回答：

1. 谁会在什么真实场景中使用，当前痛点是什么。
2. 用户提供什么输入，最终得到什么可直接使用的文件、数据或状态变化。
3. 相比普通 LLM 聊天，它增加了哪些文件处理、专业规则、工具执行、质量验证、版本管理或协作能力。
4. 它应归属 Agent、确定性 Tool 还是平台服务；不能为了增加页面数量而拆 Agent。
5. 当前技术栈是否能可靠实现，依赖、权限、成本、性能和失败边界是什么。
6. 如何通过确定性检查和必要的专业评估证明结果可用。
7. MVP 做什么、明确不做什么，以及未来如何扩展而不破坏现有协议。

产品方向获认可只代表可以继续细化，不代表其中所有能力已经获准开工。每个 MVP 仍需给用户提供清楚的选择、推荐方案和取舍，确认后再实现。

## Agent 属性分类

- 基础 Agent：产品核心能力，随 AgentFlow 默认提供，不应放到付费门槛之后。
- 可购买 Agent：面向专业场景的扩展 Agent，后续可通过插件市场、扩展包或企业版提供；MVP 阶段只预留机制，不急着做商业化。
- 可定制 Agent：允许用户调整提示词、模型、工具权限、知识范围或输出格式，但必须受平台权限、审计和验证机制约束。

一个 Agent 可以同时是“基础 Agent + 可定制 Agent”，例如总指挥 Agent 是基础能力，但后续可以允许高级用户调整规划风格。

## 正式 Agent 判定与拆分门槛

manifest、页面、action 或一段 Prompt 都不能单独证明 Agent 已实现。正式 Agent 需要同时明确：任务所有权、角色指令、模型策略、工具白名单、权限与 Guardrails、模型可见上下文、Runtime 本地上下文、输入输出协议、停止原因、运行上限和评估指标。

以下能力优先做 Tool：

- 一次调用即可确定完成的读文件、搜索、转换、写入、查询或验证。
- 不需要独立提示词、模型决策、任务所有权或专属权限策略。
- 只是某个 Agent 的一个动作，不需要单独面向用户。

只有出现以下实质差异时才拆 Agent：

- 工具或 MCP 能力面不同。
- 权限、审批或 Guardrail 不同。
- 模型、上下文或输出 schema 不同。
- 该专家需要接管一段任务/对话所有权。
- 独立后能明显改善故障隔离、trace 可读性和评估，而不只是增加角色数量。

阶段 5 默认使用 manager 模式：总指挥保持计划、任务和最终回复所有权，小 Agent 作为有边界的专业能力被调用。handoff 只在未来确实需要专家接管用户会话时引入。

人工批准属于同一次运行的 interruption。等待审批时保存待审调用和恢复状态，批准/拒绝后继续原 `runtime_task_id`；不能用新任务掩盖原来的执行链。

Agent 生命周期字段需要分开：`registered` 表示 manifest 已发现，`enabled` 表示用户允许，`runtime_ready` 表示实现和依赖可执行，`health` 表示最近自检结果，`maturity` 表示占位/实验/MVP/稳定。只有 `enabled && runtime_ready` 才能进入 Commander 的可执行计划。

## 全局 Agent 偏好草案

这些偏好建议先做成系统级配置，再允许单个 Agent 在安全边界内覆盖。偏好只能影响规划、表达、成本和交互节奏，不能绕过平台权限、审计、验证和安全边界。

### 权限确认策略

- 严格确认：编辑外部文件、联网、Shell、插件安装、数据库修改、删除/覆盖文件等操作始终询问。适合作为新手安全模式。
- 智能确认：仅对检测到的风险操作请求确认，例如删除、覆盖、执行命令、联网、访问非工作区路径；普通只读、搜索、生成草稿默认不打断。建议作为默认模式。
- 信任当前工作区：工作区内低风险读写自动放行，高风险操作仍询问。适合熟悉项目的开发者。
- 完全访问：允许更大范围访问互联网和本机文件，但必须有明显警告、会话级开启、审计日志、随时关闭入口和风险提示；不建议长期默认保存。

审批权属于用户预设的安全策略，不属于模型本身。Agent 可以建议请求权限，但不能替用户批准权限。

### 语言风格 / Agent 人格

- 专业简洁：输出短、准、偏企业办公。
- 耐心教学：多解释原因和步骤，适合新手。
- 严格审查：更关注风险、漏洞、测试和边界，适合代码审查和质量把关。
- 温和协作：语气友好，适合日常办公和跨角色协作。
- 产品顾问：更关注用户价值、流程设计、商业化和取舍说明。

人格只影响表达方式、提示密度和交互风格，不影响事实判断、权限策略、安全边界、工具能力和验证标准。

### 其他偏好

- 成本偏好：低成本 / 平衡 / 高质量。影响模型选择、上下文长度、重试次数和是否启用更强模型。
- 执行风格：先问再做 / 先给计划 / 自动推进到确认点。影响总指挥生成计划后的下一步动作。
- 输出详细度：简洁结论 / 标准说明 / 详细过程。影响 UI 展示和最终回复长度。
- 记忆开关：是否记住用户偏好、项目习惯、常用路径和常用 Agent 组合；必须可查看、可删除、可关闭。
- 失败处理策略：自动重试次数、是否换工具、是否换模型、何时停止并询问用户。

## 命令与工具执行策略草案

这部分参考 coding agent 的命令治理思想，用于回答“能不能用命令、该用什么命令、命令是否安全、是否需要用户批准”。它属于平台 Runtime / Governance 能力，不属于某个 Agent 私自决定的权限。

### 命令风险分级

- 只读定位命令：用于查看文件、搜索代码、检查状态，例如 `rg`、列目录、读取文件、`git status`、`git diff`、`git log`。默认低风险，但仍必须限制在工作区或用户授权目录内。
- 诊断验证命令：用于编译、测试、类型检查、lint、脚本验证，例如 `pytest`、`python -m compileall`、CMake 构建、npm 测试。可能产生缓存或构建产物，默认中风险，应在任务计划中说明目的、工作目录和预计耗时。
- 修改型命令：格式化、代码生成、迁移、包管理安装、写入文件、修改配置、应用 patch。默认需要确认，除非用户选择了信任当前工作区且命令被策略允许。
- 联网命令：下载依赖、访问外部 API、拉取仓库、上传数据。默认需要确认，并要说明访问目标和可能泄露的信息。
- 高危命令：删除、覆盖、批量移动、`git reset --hard`、强制 checkout、清空目录、修改系统路径、提权、执行未知脚本、`curl | sh` 等。默认禁止或逐次强确认，即使完全访问模式也必须审计。

### 命令选择原则

- 精确定位优先用低成本只读工具，例如 `rg`、文件列表、读取目标文件，不默认做大范围递归扫描。
- 能用项目已有脚本和测试命令时，优先使用项目脚本；不要临时拼高风险 shell。
- 执行前要知道命令目的、工作目录、输入参数、预期输出和失败后的处理方式。
- 命令输出要限制长度，敏感信息要脱敏，超时要中断，失败要结构化记录。
- 对同一命令连续失败要有失败计数，超过阈值停止自动重试。
- 尽量使用结构化工具调用；确实需要 Shell 时，命令必须经过风险分类和权限策略检查。

### 通用代码 Agent 决策与外部代码工具约束

2026-08-14 已确认不自研通用代码工坊 Agent。原因不是代码能力不重要，而是通用编程已由 Codex、Claude Code、Cursor 等成熟产品覆盖；AgentFlow 从头追赶会消耗大量开发和验证成本，也难形成面向客户的差异化交付。

- 现有 `code_agent` manifest、Node Contract、命令安全检查和 Qt 占位只算历史兼容或平台资产，不代表该 Agent 已立项、可运行或等待继续开发。
- 命令治理、workspace 边界、权限确认、审计、产物和 Verifier 继续保留，因为其它专业 Agent 或外部 Runtime 同样会需要这些能力。
- 未来若接入成熟外部代码 Agent，应作为受控 Adapter 单独立项；必须明确允许目录、只读/写入边界、命令白名单、联网、密钥、超时、取消、产物归属和失败责任。
- 外部代码 Agent 不能绕过 AgentFlow 的权限策略，也不能接管客户任务、任务历史或最终产品状态。
- 除非用户明确重新开启该产品方向，不再为“代码工坊页面看起来完整”补模型循环、Shell、依赖安装、自动改码或测试执行。

### 专业 Agent 逐项讨论规则

- 一次只讨论一个候选 Agent；候选名称不等于立项，用户明确认可方案后才把状态改为“已确认”并开始实现。
- 每个候选先回答：谁会付出真实时间或费用使用、当前痛点是什么、最终交付什么可用文件/数据/状态变化、为什么普通聊天不能直接替代。
- 再评估：现有技术栈能否稳定实现、需要哪些 Tool/Provider/Runtime、权限与隐私边界、失败如何降级、MVP 明确不做什么。
- 必须给出基础/可购买/可定制属性、客户最短输入、主工作流、Verifier 和可实际操作的验收用例。
- 功能在精不在多。若核心价值只是“换一种提示词让 LLM 回答”，降为通用能力或某个工作流步骤，不新建 Agent 页面。
- DeepSeek Harness、MCP、RAG、视觉模型等只在该候选的客户交付确实需要时选用，不为了使用技术而扩大 Agent 范围。

- 默认输出详细度：标准说明。

- 命令/工具策略：不直接执行命令；只在计划中声明需要哪个 Agent 或 Runtime 工具执行，并标出风险、工作区范围和是否需要确认。

### 第一版产品定位与工作流

总指挥不是“万能聊天 Agent”，而是 AgentFlow 的任务控制平面：它让用户用一句目标发起工作，把材料、专业能力、权限、预算和完成标准组织成可理解的计划，并持续管理该计划直到交付或明确停止。

第一版优先复用 AI 调度台，不新增一个堆满配置的独立大页面。客户流程固定为三段：

1. **任务输入**：输入目标，显式选择材料，显示本次权限与模型质量模式。
2. **计划确认**：展示 1 至 4 个步骤、预期交付物、风险、预算与需要确认的动作；客户可以修改或确认。
3. **执行与交付**：以父任务时间线呈现真实子任务、等待确认、失败恢复和最终产物，不展示未验证的模型思维过程。

文档助手与数据工作台均属于总指挥应认识的专业能力。总指挥可以为它们生成计划、说明材料与交付边界；但只有某个具体 action 通过 `enabled && runtime_ready && health=ready` 的准入检查后，才能真正创建子任务。数据工作台当前只开放 D5.4 的 `analyze_dataset`：必须显式绑定一份已导入的 CSV/XLSX，创建只读分析子任务，父任务仅保留短结论、源哈希和统计数量；不向父任务、模型或长期记忆传递原始/预览行，也不生成、修改或导出文件。其余数据动作仍由客户在数据工作台直接确认。

### 当前 C0/C1/C2/C3 实现边界

- Action 准入目录是唯一的客户执行判断来源：总指挥、文档助手和数据工作台的 action 都声明材料类别、执行模式、确认语义、验证范围与恢复提示；`enabled` 或页面可见本身不能放行执行。
- 调度台只传递客户显式选中的工作区相对材料引用。无绑定材料时，总指挥只能澄清，不扫描工作区猜测文件；绝对路径、`..` 跳转和不匹配的文件类型会被拒绝。
- 文档 action 通过准入后可沿现有文档助手父子任务链真实执行。数据 `open_workspace` 是 `guided_handoff`：Runtime 记录阻塞与用户下一步，但不会读取数据、创建子任务或伪造已完成结果。
- 真实执行前的确认窗口会显示计划摘要、步骤、读取范围、写入范围与外部服务，避免用户确认一条看不见边界的泛化提示。
- 父任务完成时会把专业 Agent 的状态、短结论、关联任务 ID 和下一步收束为历史复盘；完整来源、模型输出和 Tool trace 仍保留在子任务，避免重复存储客户材料。
- C2 的长期层是用户显式确认的 SQLite 短事实，当前支持 `user_preference`、`project_constraint`、`experience`；系统设置默认关闭读取，开启后 Commander 才按标题、标签和摘要的轻量关键词检索最多三条，并在 `memory_context_summary` 与计划假设中说明实际引用。模型不拥有记忆写入权。
- Qt 已提供“系统设置 -> 管理记忆”的查看、新建、编辑、停用、删除和全局清空确认入口；创建时服务端拒绝密钥、令牌、私钥、绝对路径、原文档和完整对话。调度台使用紧凑图标设置记忆范围，任务历史只对已完成 Runtime 总指挥任务显示“记住约束”；候选在独立确认窗口中可编辑类型、范围、标题、摘要与标签，普通一次性任务不产生候选。
- C3 已完成不可变计划版本：每一版计划以 `task_id + plan_version` 保存，旧快照可读取但不可设回或覆盖；修订 API 只接受已确认的新目标与变更说明，重新运行服务端准入/dry-run，拒绝客户端传入步骤、权限或路径。来源任务已经派生 Runtime 时必须新建任务，不能修改当前计划。Qt 主调度台仅提供“查看计划”轻入口，独立的可调整 Inspector 按需加载版本表和详情，并在确认后提交下一版；一旦进入 Runtime，输入区自动转为只读。
- C3 的权限 interruption 已保留同一 runtime 的完成步骤、产物和事件并从等待点继续，恢复日志会留下 `task_resumed`。`/start` 先持久化任务并由同进程后台 worker 执行，Tool 边界会 checkpoint；WebSocket 推送任务排队、启动/恢复、步骤、权限、暂停、取消与终态等阶段事实。用户可在历史页发起暂停、取消和继续，Runtime 只在 Tool 安全边界响应，已完成步骤不会重跑。服务进程重启时，遗留 `pending/running/waiting_permission` Runtime 会安全进入 `blocked` 并标记中断步骤/工具，客户只能复核后 retry；自动续跑、强制中断模型/HTTP 调用和 token 逐字输出仍未实现。任务结束后仅对明确长期表达提出候选，绝不自动写入。
- **C5.1 知识库深度委派：**仅当客户在 AI 调度台明确绑定一座资料库，并在目标中明确要求“深度分析、全库总结、整库分析、逐章总结或深度报告”时，Commander 才会生成 `knowledge_agent/deep_summary`。该步骤要求独立的 `knowledge_deep_analysis` 预算确认；即使用户选择“完全访问”也不会静默跳过。确认后 Runtime 只冻结当前活动索引范围、创建 `task_k4_*` 后台子任务并登记 `agentflow-task://` 关联，父任务的“已完成”只代表委派受理成功，绝不代表 Map/Reduce 或报告已经完成。最终范围、阶段、暂停/继续/取消、失败恢复和报告导出继续在 K4 子任务内查看。
- C5.1 不从单一资料库绑定推断“资料对照表”：对照仍必须在知识库工作台由客户显式选择 2 至 12 份资料；不开放 OCR、联网、写入、跨库自动扫描或自动把普通可信问答升级成深度任务。
- **C5.2 父子状态镜像：**历史页的 Commander 复盘会按需读取关联 `task_k4_*` 的 SQLite 状态与按 action/status 聚合的计数，展示真实子任务状态及 `Map 完成/总数`、`Reduce 完成/总数`。它不读取 `run_json`、章节正文、Map 小结、来源、模型输出或子任务摘要；子任务仍是唯一的检查点、暂停/继续/取消、正式报告与完整 trace 所有者。只要关联子任务处于 `queued/pending/running/waiting_permission`，父任务详情继续低频自动刷新，避免父任务“交接完成”被误解为全部工作已完成。
- **C5.3 关联工作台入口：**父任务历史的关联 K4 artifact 点击“打开”时，Qt 直接以既有稳定 `task_k4_*` 打开知识库深度任务工作台的关联模式。该模式只补读同一任务的 scope、状态和 checkpoint，隐藏“新建分析”输入，将阅读空间留给结果、范围和控制；不会创建新任务、再冻结范围、读取原始章节或把 K4 控制权移交给 Commander。运行中的活动指示器只由子任务真实状态驱动，暂停、失败、取消和完成后停止。

### 主要能力

- 理解用户目标，判断是聊天、规划、现有文档交付、已批准的专业任务还是混合任务；遇到通用代码需求时可说明外部工具路线，但不能调度未立项的内置代码 Agent。
- 当用户目标过于模糊、缺少文件、缺少路径、缺少输出格式或缺少验收标准时，先提出 1-3 个关键澄清问题，不硬猜。
- 建立“材料绑定”：只把用户明确选择或当前任务已经授权的文档、数据集、任务产物绑定进计划；不能依据文件名猜测、扫描任意本机目录或把原始数据默认送入模型。
- 在计划开始前提炼完成标准，例如产物类型、保存位置、测试是否需要通过、是否需要用户确认。
- 读取 Agent Registry 和 Node Contract，选择合适的 Agent 与工具。
- 路由前检查 `runtime_ready/health/maturity`；未就绪能力只能解释缺口或建议后续方案，不能生成看似可执行的步骤。
- 为每个候选动作读取 Agent 准入资料：允许的输入类型、预期产物、最大风险、确认点、超时/重试预算、Verifier 与失败恢复语义；页面存在或 manifest 已发现都不构成准入。
- 生成结构化 `workflow_plan`，包含步骤、依赖、理由、预期产物、风险级别和所需权限。
- 支持计划版本，例如 `plan_v1`、`plan_v2`；用户调整步骤、删除步骤或更换 Agent 后，要保留版本关系和变更摘要。
- 给出预算预估，包括大概步骤数、耗时等级、模型成本等级、需要的权限和最高风险等级。
- 区分 dry-run 与 runtime：先预演解释，再在用户确认后交给 Runtime 执行。
- 支持执行控制语义：暂停、取消、继续、重试、跳过某一步；实际执行仍交给 Runtime 和具体 Agent。
- 识别高风险步骤，触发权限确认，而不是自己绕过权限。
- 根据用户的权限确认策略、语言风格、成本偏好、执行风格和输出详细度调整计划呈现与下一步建议。
- 当多个 Agent 输出冲突时，汇总差异、给出依据和建议；关键冲突交给用户裁决，不偷偷替用户决定。
- 任务结束后生成轻量复盘，包括成功/失败原因、耗时、工具调用情况、可改进点和是否值得写入记忆。
- 在计划中说明工作区边界：本次任务可能读取、写入或影响哪些文件、目录、外部服务和权限范围。
- 汇总任务进度、失败原因、下一步建议和最终结果。
- 在计划失败时给出可理解的修正建议，例如缺少文档、权限未确认、工具参数不足、Agent 不可用。
- 以父任务拥有计划与最终回复、专业 Agent 拥有子任务与专业 trace 的方式协调执行；父任务只汇总已验证的子任务结论、产物和下一步，不能用模型编造子任务完成状态。

### 明确不做

- 不直接写文件、执行 Shell、联网访问、安装插件或修改数据库。
- 不亲自承担文档制作、数据处理、专业审查等具体交付职责，也不把普通模型回答包装成已完成的专业任务。
- 不隐藏高风险操作，不替用户默认批准权限。
- 不让 Agent 人格影响事实判断、安全策略、工具权限或验证标准。
- 不因为用户选择“完全访问”就省略风险提示和审计记录。
- 不在信息不足时硬生成看似完整的计划；缺关键条件时先澄清。
- 不把计划版本覆盖掉旧版本；用户需要能看出计划怎么变了。
- 不替专业 Agent 或 Runtime 执行暂停、取消、重试之外的真实副作用操作。
- 不把所有历史对话塞进上下文；只使用当前任务、必要摘要、Agent 能力清单和任务状态。
- 不绑定单一模型供应商；模型只能通过 `ModelGateway` 选择。
- 不默认把 Node.js DeepSeek Harness 当作总指挥聊天或执行主链路；它只能在 `RuntimeRouter` 中作为满足明确场景、开关、Provider、权限和回退条件的可选后端。
- 不把 manifest 的 `enabled`、页面可见或 Node Contract 存在误判成 Runtime 已就绪。

### 输入

- 用户自然语言任务。
- 当前可用 Agent 列表和 manifest。
- Node Contract 能力、权限和失败码。
- 当前模型配置状态。
- 全局 Agent 偏好：权限确认策略、语言风格、成本偏好、执行风格、输出详细度和记忆开关。
- 用户明确选择的文档、数据集、已有产物和当前 workspace 线索。
- 可选的会话摘要、项目约束、稳定用户偏好与可复用经验；每条长期记忆都必须带作用域、来源、更新时间、敏感性和用户控制状态。
- 可选的当前 plan 版本、用户修改意见、任务运行态和已有 Agent 输出。

### 输出

- `workflow_plan`：结构化计划。
- `summary`：给用户看的短摘要。
- `clarifying_questions`：任务缺关键条件时提出的澄清问题。
- `definition_of_done`：本次任务完成标准。
- `plan_version` 和 `change_summary`：计划版本与变更摘要。
- `budget_estimate`：步骤数、耗时等级、模型成本等级和权限风险摘要。
- `workspace_scope`：预计读取、写入或影响的文件、目录、外部服务和权限范围。
- `max_risk_level` 和 `requires_confirmation`：风险与确认提示。
- `validation_errors`：计划校验失败原因。
- `next_action`：建议用户继续执行、补材料、确认权限或修改任务。
- `preference_applied`：本次计划应用了哪些用户偏好，例如权限策略、输出详细度和成本模式。
- `conflict_summary`：多个 Agent 输出冲突时的差异、依据和建议。
- `task_retrospective`：任务结束后的轻量复盘。
- `memory_context_summary`：本次实际使用的最小化记忆摘要与来源范围，不回显无关长期记录。
- `memory_proposals`：建议写入、更新或遗忘的长期记忆候选；高敏感或影响范围大的内容必须等待用户确认。

### 上下文与长期记忆

总指挥把“运行时会话”与“产品长期记忆”分开管理，不能让某个模型或 Harness session 成为用户记忆的唯一载体：

| 层级 | 保存内容 | 使用规则 |
| --- | --- | --- |
| 会话记忆 | 当前目标、选中材料、计划版本、审批和子任务状态 | 每次任务自动保存，用于暂停、继续和失败恢复。 |
| 用户偏好 | 语言、表达风格、质量模式、默认确认方式、常用交付习惯 | 仅保存稳定且非敏感的偏好；用户可随时查看、编辑、删除或关闭。 |
| 项目记忆 | 已确认目标、技术路线、术语、关键约束、已作决策 | 必须有项目作用域和来源任务，过期或被新决策替代时可回溯。 |
| 经验记忆 | 已验证的工作流模板、失败原因、用户否决过的方案 | 只记录可复用的摘要与结果，不复制原始私密材料或完整模型对话。 |

第一版使用 SQLite 的结构化记录、标签与标题/摘要关键词检索；检索只注入与当前任务有关的最多三条摘要。全文索引、向量检索、长期知识库和跨项目语义召回属于后续增强，不能为了“有记忆”而把全部对话和文件全量嵌入。API Key、认证信息、绝对敏感路径、原始表格行和未经授权的材料永不写入长期记忆。

### workflow_plan 协议字段草案

MVP 阶段先把协议做稳定，不追求一次覆盖所有未来场景。字段命名优先可读、可验证、可被 Qt 直接展示。

```json
{
  "schema_version": "agentflow.workflow_plan.v1",
  "plan_id": "plan_xxx",
  "plan_version": 1,
  "parent_plan_id": null,
  "change_summary": "",
  "intent": "document_code_report",
  "user_goal": "用户原始目标",
  "summary": "给用户看的计划摘要",
  "clarifying_questions": [],
  "assumptions": [],
  "definition_of_done": [],
  "preference_applied": {
    "permission_policy": "smart_confirm",
    "personality": "professional",
    "cost_mode": "quality_first",
    "execution_style": "plan_then_confirm",
    "detail_level": "standard",
    "memory_enabled": false
  },
  "budget_estimate": {
    "step_count": 0,
    "time_level": "low",
    "model_cost_level": "low",
    "requires_network": false,
    "requires_command": false
  },
  "workspace_scope": {
    "read_paths": [],
    "write_paths": [],
    "external_services": [],
    "notes": ""
  },
  "max_risk_level": "low",
  "requires_confirmation": false,
  "steps": [],
  "validation_errors": [],
  "next_action": "execute_after_confirm"
}
```

`document_code_report` 是当前 Commander 协议中的历史兼容 intent 值，不代表 Code 或 Report 仍是待开发的独立 Agent；报告交付由 Document Agent 承担，通用 Code Agent 已取消自研立项。协议重命名需与后端迁移和兼容策略一并处理。

`steps[]` 建议字段：

- `step_id`：稳定步骤 ID，例如 `step_document_search`。
- `title`：用户可读标题。
- `agent_id`：负责该步骤的 Agent。
- `action`：Agent 动作名，例如 `document.search_text`。
- `tool_name`：Runtime 真实工具名，可为空。
- `input`：结构化输入，必须可校验。
- `depends_on`：依赖步骤 ID 列表。
- `reason`：为什么安排这一步。
- `expected_output`：预期产物或状态变化。
- `required_permissions`：权限列表。
- `risk_level`：`low` / `medium` / `high`。
- `requires_confirmation`：是否需要确认。
- `command_policy`：如果可能运行命令，写明命令风险等级、是否允许、是否需要确认。
- `success_criteria`：该步骤怎样算成功。
- `timeout_ms`：建议超时。
- `retry_policy`：最大重试次数、是否可重试、停止条件。

### 澄清与直接规划规则

- 直接规划：用户目标、输入材料、输出形式、风险范围基本清楚，且不涉及未说明的高风险操作。
- 先澄清：缺少关键文件/目录、输出格式、目标对象、执行范围、权限范围，或同一句话可能对应多个 Agent 路线。
- 先拒绝或转人工确认：用户要求绕过权限、删除/覆盖不明确范围、执行未知脚本、上传敏感信息或进行平台禁止的操作。
- 澄清问题最多 1-3 个，优先问会改变执行路线的问题，不问无关细节。
- 如果用户选择“自动推进到确认点”，总指挥仍要在高风险步骤前停下等待确认。

### 可调用工具

- Agent Registry 查询。
- Node Contract 查询。
- Workflow Validator。
- Task Repository 读写任务状态。
- ModelGateway 规划调用。
- 权限请求创建接口。
- Runtime 状态查询与控制请求接口，例如暂停、取消、继续、重试、跳过。

总指挥不直接调用文件写入、Shell、联网或插件工具；这些只能由 Runtime 按步骤和权限边界执行。

### 权限边界

- 默认低权限：只能生成计划、读取 Agent 能力、读取必要任务状态。
- 不能执行真实副作用操作。
- 可以创建权限请求，但不能替用户批准。
- 权限确认策略由平台安全层执行，总指挥只能读取策略并在计划中标记风险。
- 后续可允许企业管理员配置总指挥的规划风格、默认模型、风险阈值和允许的最高权限模式。

### 协作对象

- 文档助手 Agent：完成受控文件处理、正式文档/PPT 交付和专业文档审查；读取、摘要和提取是内部步骤，不再作为主要产品定位。
- 数据工作台 Agent：完成本地受控数据画像、结论、图表和字段副本交付；总指挥已准入唯一的 `analyze_dataset` 只读 action。它只接收一份显式绑定的数据集，复用本地白名单计算并回传可审计摘要；图表/工作簿交付和字段副本仍必须由客户在数据工作台直接确认。
- 外部成熟代码 Agent（未来可选）：只在单独立项后通过受控 Adapter 提供代码任务能力，不属于当前内置 Agent，也不能绕过平台命令与权限治理。
- 平台检索服务：统一提供精确搜索、按需语义检索和来源定位，不单独占用一个 Agent 页面。
- 共用 Verifier/Evaluator：按产物类型执行质量检查，并把问题反馈给原 Agent 或用户，不单独占用一个应用页面。
- 未来插件 Agent：按 manifest 和权限加入计划。

### 失败处理

- 计划校验失败：返回错误字段和修复建议，不进入执行。
- 关键信息不足：先返回澄清问题，不生成高风险执行计划。
- 找不到合适 Agent：向用户解释缺少能力，并建议安装、启用或换任务描述。
- 模型输出不合规：最多重试有限次数，仍失败则退回规则规划或要求用户确认。
- 权限未确认：任务停在等待状态，不自动继续。
- Agent 输出冲突：进入仲裁摘要，必要时等待用户选择。
- 执行中失败：根据失败策略建议重试、跳过、换 Agent、换模型或停止。

### 评估指标

- 计划可执行率：生成的 plan 是否通过 validator。
- 任务成功率：用户目标最终是否完成。
- 低返工率：执行中是否频繁改计划或因参数错误失败。
- 工具选择准确率：是否选对 Agent 和 action。
- 澄清有效率：是否用少量问题补齐关键条件。
- 计划变更成本：用户修改计划后是否能稳定生成新版本。
- 用户可理解度：风险、权限、失败原因是否清楚。
- 成本与效率：步骤数、模型调用次数、耗时和 token 是否合理。

### UI 入口

- AI 调度台：主要入口。
- 历史任务页：查看计划、运行态、权限、日志和结果。
- 后续系统设置：配置总指挥规划风格和风险偏好。

### MVP 验收标准

- 用户输入一个混合任务后，总指挥能生成可校验 `workflow_plan`。
- plan 能说明每一步为什么做、由哪个 Agent 做、预期产物是什么。
- 信息不足时能提出 1-3 个澄清问题，而不是胡乱计划。
- plan 能显示完成标准、预算预估、工作区边界和最高风险。
- 用户修改计划后能生成新版本，并说明变更。
- 高风险步骤必须显示权限确认。
- dry-run 与真实执行边界清楚。
- 支持暂停、取消、继续、重试等控制语义的计划层表达。
- 失败时能告诉用户缺什么、卡在哪里、下一步怎么做。
- 任务结束后能生成轻量复盘。

### MVP 落地验收清单

- 信息不足用例：用户只说“帮我整理这个”，总指挥应提出澄清问题，而不是直接生成高风险计划。
- 文档交付用例：用户提供受控 workspace 文档并要求“先核验项目风险，再制作汇报 PPT”时，应生成 Document Review -> Presentation Delivery 的可校验计划；需要写出文件时必须标记确认点。
- 数据任务用例：用户选择一份受控 CSV/XLSX 并要求分析趋势时，总指挥可以生成 `analyze_dataset` 只读子任务并直接在会话交付结论；生成图表、分析工作簿或字段副本时，总指挥必须先给出受限计划，客户用自然语言确认后由 Runtime 写入新 artifact 并回到同一会话展示。未选择数据、选择多份但没有声明关联方式、或字段意图不明确时必须澄清，不能越过写入边界或要求客户为了完成任务跳回数据工作台。
- 高风险命令用例：用户要求“运行安装脚本并改项目”，计划必须标记联网/命令/写入风险，并等待权限确认。
- 计划修改用例：用户要求删除第 2 步或换 Agent，应生成新 `plan_version` 和 `change_summary`。
- 预算展示用例：计划应显示步骤数、耗时等级、模型成本等级、是否需要命令/联网和最高风险。
- 工作区边界用例：计划应列出预计读取/写入的受控路径，不能把本机任意路径当作默认范围。
- 执行控制用例：运行中任务应能表达暂停、取消、继续、重试的下一步建议。
- 冲突处理用例：两个 Agent 输出互相矛盾时，应生成 `conflict_summary` 并等待用户或策略裁决。
- 任务复盘用例：任务结束后应说明成功/失败、耗时、工具调用情况和是否建议写入记忆。
- 长期记忆用例：任务只注入当前相关的用户/项目摘要；用户删除或关闭某条记忆后，后续计划不得继续引用它。敏感、原始材料或无来源的模型推测不得成为记忆。
- 安全回归用例：选择完全访问模式时仍要保留风险提示、审计和关闭入口。

### 后续扩展

- 扩展记忆治理：项目归档、过期策略、冲突决策、导出/清除与后续语义检索。
- 支持多策略规划：快速模式、稳妥模式、低成本模式。
- 接入 LangGraph / LangChain 作为复杂编排实现层，但不改变 AgentFlow 自己的协议、权限和审计边界。
- 支持企业策略，例如禁用某类工具、限制模型供应商、强制人工审批。

### MVP 主要能力

- 处理受控 workspace 内 1MB UTF-8 `txt`、`md`、`markdown`，以及 10MB `pdf`、`docx`；Qt 导入入口不接收任意本机路径。
- 用户必须在 Qt 页面明确选择本次材料；未选择且 workspace 有多份文档时返回澄清，不擅自选错。
- 关键信息卡使用单份明确选择的材料，按 `subject/purpose/scope/stakeholders/deliverables/milestones/risks` 固定字段提取明确事实；每项必须带来源，无证据字段不补写，结果在详情页中以可追溯字段表呈现。
- 结构化大纲使用单份明确选择的材料，输出带来源的 `outline_sections[]`：每项包含稳定章节 ID、标题、写作意图和关键要点；它只提供用户审阅的创作前蓝图，不生成正文、不创建、覆盖或导出文件。
- Markdown 草稿预览使用单份明确选择的材料，输出 `draft_title` 和带来源的 `draft_sections[]`：每项包含稳定章节 ID、标题与正文。预览本身不写文件；用户从独立结果详情页输入 `.md` 文件名并二次确认后，`POST /api/agents/document_agent/{task_id}/save-draft` 只会将该已验证结构写入 `output/document_drafts/`。客户端不能指定目录或绝对路径，后端拒绝路径分隔符、默认不覆盖同名文件；首次保存后 UI 会提供“另存为 Markdown”并建议副本文件名，每一份 UTF-8 文件都会保留每章来源脚注，并以独立 `artifact_saved` 事件和 Markdown artifact 追加到原任务历史。
- 草稿详情页也提供“复制 Markdown”：只把当前 Guardrail 已验证的标题、章节正文和章节来源脚注写入系统剪贴板，不触发后端请求、文件写入、覆盖或任务状态迁移；用户可先复制到外部编辑器，再决定是否回到本页走受控保存。
- 分章节创作预览使用用户在已完成草稿中明确选择的一个章节和一条创作指令；`POST /api/agents/document_agent/{task_id}/draft-sections/start` 只从源任务恢复受控文档引用与章节身份，再次读取同一份工作区材料，生成一个带来源的独立子任务预览。Runtime 强制保留原章节 ID 与标题，输出只能包含这一章；不改写原草稿、不修改任何已保存 Markdown、不自动创建新文件。子任务失败时客户端保留原草稿详情，用户可以继续审阅或保存。
- 本章审校与修订预览采用两步、两种边界：`draft-sections/review/start` 会重新读取材料，只返回原文片段、候选建议、理由与来源；`draft-sections/revision-preview/start` 只接受一条 `suggestion_id`，`draft-sections/revision-batch-preview/start` 接受同一审校任务的 2 至 6 条 `suggestion_ids`。服务端确认每个目标片段在章节中唯一出现、批量片段不重叠后才按原文位置倒序生成“修改前 / 修改后”与完整新草稿。修订步骤不调用模型或 Tool，不改写任何旧任务或文件；用户认可后仍需调用 `save-draft` 命名、确认并另存新的 UTF-8 Markdown，默认不覆盖旧版本。每个可保存草稿快照同时携带 `draft_version`：版本 ID、根草稿、直接父任务、类型和变更摘要会写入结果、Markdown 注释及 artifact 元数据，供任务历史回看和安全另存。`restore-preview/start` 只接受历史 task ID，从已完成任务恢复 `draft_title/draft_sections/sources` 为新的独立版本；它必须再次核对源版本 ID，且零模型、零 Tool、零文件写入，用户仍需另走保存确认才能交付。
- 用户手动修订只允许在已完成草稿的单个章节内进行，并通过独立编辑窗输入正文；它不会伪装成模型建议或已验证来源。新预览保留历史来源仅供回看，不能直接保存；事实核验会把未通过的状态保留为 `reviewed_with_questions`，直到用户解决待确认项并重新核验。
- 跨文档问答、整合和对比要求用户明确勾选 2 至 4 份材料；Runtime 必须从每份文件开头连续读取。问答与整合的 `answer_source_ids` 必须直接关联至少两份不同文件的来源；对比模式的每项共识、差异或缺失结论也必须同时关联至少两份不同文件的来源。超出四份时 Qt 在提交前明确提示，不把后端 422 直接抛给用户。
- 使用 `document.search_text` 和 `document.read_text` 获取必要片段，避免默认把所有文档全文塞进模型。
- 基于真实读取结果生成摘要、需求、约束、待办、实体和待确认问题。
- 每条关键结论必须带来源：Runtime 生成 `source_id` 后映射为文档名、受控相对路径、文本行号、PDF 页码或 DOCX 段落/表格定位和短片段。
- 同时返回用户可读回答和结构化 `document.context`，方便后续已批准的专业 Agent 与文档交付工作流消费。
- 信息不足或没有命中时明确说明“没有足够依据”，不得补写成看似来自文档的事实。

### 产品方向重审（2026-07-31 已认可）

文档助手重新定位为“帮助用户完成真实文档工作并交付可用产物”，不再以摘要、需求抽取、关键信息卡、大纲、单文档问答、跨文档问答或整合作为一级卖点。现有能力先作为兼容入口和内部基础保留，后续随新工作流逐步收进任务步骤、快捷配方或高级选项，不盲目删除已经验证的来源追踪、长文档读取、版本链和审计能力。

已认可、允许继续细化的三个产品方向：

1. **文件转换与处理**：围绕真实文件完成格式转换、拆分合并、批量处理、压缩、页码/水印等确定性任务，并交付可打开的文件。具体格式矩阵、是否保真、批量上限和覆盖策略必须逐项确认；转换引擎属于 Tool，文档助手负责编排、权限、状态和交付。
2. **智能文档与 PPT 制作**：从资料、主题或已有模板出发，完成内容组织、版式生成、素材协作、预览、质量检查和 DOCX/PPTX/PDF 等正式产物交付。摘要与大纲只是中间步骤；PPT 的图片生成/选择和数据图表可调用未来的视觉、数据能力，不应把所有专业能力复制进文档助手。
3. **文档审查**：按论文、合同之外的正式材料、项目文档等明确审查配置，输出带位置、严重度、依据和修改建议的问题清单，并支持用户确认后的修订工作流。论文审查可先做结构、引用对应、格式和语言一致性；没有可靠数据库或外部资源时，不承诺查重、学术创新性或法律结论。

以上是产品方向，不代表三个方向下的所有功能包都已批准。已完成的受控交付闭环包括下方的“PDF 整理基础版”“项目方案 PPT v1”“项目文档审查 v1”和“论文审查 v1”；PDF 定位为辅助文件工具，不作为文档助手的主卖点。其余文件处理、PPT 模板/素材、增强审查能力仍须逐项明确目标用户、输入输出、支持范围、权限、依赖、Verifier 和验收用例后再开发。后续可以扩展新方向，但每个候选都必须通过本文“产品功能立项门槛”。

### 已确认 MVP：PDF 整理基础版

- 场景：用户需要合并 PDF、提取页面、旋转误扫页面或删除多余页面，并得到可直接使用的新文件。
- 操作：合并选择 2 至 12 份 PDF 并按勾选顺序处理；提取、旋转、删除一次选择 1 份 PDF，页码使用 `1-3,5` 格式，旋转支持顺时针 90、180、270 度。
- 交付与验证：结果固定写入 `output/document_processing/`；生成后重新打开并核对页数，Qt 可直接打开已验证产物，完整阶段与 Tool 审计进入任务历史。
- 安全边界：二次确认明确“原文件不会被修改、覆盖或删除”；只允许 workspace PDF，单文件导入上限 10 MB、单次输入总量 50 MB、总页数 1000、输出 100 MB。
- 明确不做：加密/损坏 PDF、OCR、压缩、水印、格式转换、批量队列、原地覆盖或工作区外路径访问；这些必须作为后续独立 MVP 讨论。

### 已确认交付路线：PPT 制作、项目审查、论文审查

用户已确认三条路线都要做，但采用共享底座、逐条闭环的顺序，而非同时堆叠页面和模型模式：

1. **项目方案 PPT 工作台 v1（已完成）**：只接受已有的、带来源且已核验的文档草稿。系统会先自动重读草稿实际引用的受控材料，按项目审查规则完成范围、验收、责任、节点、风险依赖与术语预检；预检结果与来源随逐页计划一起展示，不要求客户额外点击审查按钮。客户只确认最终写入，随后系统以固定“专业项目方案”模板生成可编辑 `.pptx`。首版包含封面、目录、章节内容、总结与来源页；每页绑定草稿章节和来源，Verifier 会重新打开 PPTX，核对页数、已确认标题、内容页要点和唯一来源页。
2. **项目文档审查 v1（已完成）**：面向 PRD、项目方案、需求说明，按需求完整性、术语一致性、责任边界、验收可测性、时间/依赖冲突输出带位置、严重度、依据和建议的审查报告。它不替代法律、财务或行业认证。
3. **论文审查 v1（已完成）**：在独立规则配置下检查论文结构、标题层级、引用对应、图表提及、格式线索和明显可读性问题。它不声称查重、识别学术创新性、判定抄袭或给出学术/法律结论。

PPT v1 的输入、交付与边界：

- 输入：一个完成的、`draft_verification_state=verified` 的文档草稿快照；用户可选择“项目方案”交付类型并在文件写入前二次确认。客户端不能提交任意正文、模板路径或输出路径。
- 输出：`output/document_presentations/` 中的唯一 `.pptx`，带标准 artifact、历史事件、来源摘要和打开入口。原草稿、原材料、旧交付物均不被修改或覆盖。
- 技术：使用 `python-pptx` 的固定内置模板生成 Office 可编辑对象；模型只负责现有草稿内容，不介入文件写入、路径、引用位置或版式安全边界。
- 当前不做：上传企业模板、图片生成、没有可靠数据源的图表、PowerPoint 原生动画、任意主题自由设计、PPTX 反向编辑、PDF 导出或声称像专业设计师一样自动完成全部视觉设计。

PPT v1 实现状态：后端提供 `POST /api/agents/document_agent/{task_id}/presentation-preview` 和 `POST /api/agents/document_agent/{task_id}/presentations/export`；预览 `plan_id` 绑定草稿版本、章节正文和来源，草稿变化后旧确认会被拒绝。用户确认后，`python-pptx` 只会在 `output/document_presentations/` 新建不重名的 `.pptx`，并把 artifact 与事件追加到原文档任务。Qt 在结果详情页提供“导出项目 PPT”入口，完整逐页计划与文件名放在独立确认窗口中，不挤占分析工作台。离线脚本 `backend/scripts/verify_presentation_delivery.py` 已覆盖未确认、过期计划、导出、PPTX 回读、artifact 追溯与同名文件拒绝。

### 已确认：PPT 制作 V2（V2.2 已实现，继续客户体验验收）

#### V3 智能制作分阶段路线

- 已完成：四套内置主题与受控内容版式，避免把“换颜色”误称为换模板；无可靠数据时不生成伪图表。
- 已完成软件接入、进入稳定性验收：内置主题与版式始终适用，配图来源可选不添加额外配图、Pexels 摄影图片或 Seedream AI 配图。计划阶段不联网、不生成图片；确认导出后才调用对应 Provider。Seedream 最多生成 4 张请求无可见水印的横向图片，原始字节只留在导出内存并嵌入 PPTX，任务历史仅保存模型、页面意图、提示词摘要与来源类型。
- 进行中：智能研究、联网数据与图表。已完成 Wikimedia 来源参考、World Bank 固定指标快捷通道、首次模型通用研究蓝图，以及第一版统一 ResearchGateway：用户确认后通过 Tavily 或 DeepSeek 官方原生搜索取得候选来源，受控读取公开页面，再由第三次模型只依据来源片段抽取数据；Verifier 拒绝来源、对象、单位或时间口径不一致的数据。导出阶段事件已进入 Qt 与任务历史；`auto` 的 Tavily 零候选/不可读正文只可在剩余查询预算内回退 DeepSeek。完整协议与验收门槛见 `docs/PPT_RESEARCH_DATA_DESIGN.md`。真实通用主题稳定验收和多 Provider adapter 仍未完成。
- 未开始：PowerPoint 原生动画。它需要独立的 Office 兼容预检、生成与回读 Verifier；第三步通用数据主题未通过真实验收前不得提前进入。
- 当前风险：Seedream 账号权限、服务繁忙或内容策略可能随时使单张生成失败；系统应把 `ModelNotOpen`、授权、限流与超时转成明确可操作的 warning 并回退内置版式，不得使整个 PPT 导出失败，也不得假称生成成功。

PPT V2 是文档助手内的第二条演示文稿交付路径，不新增营销式 Agent。目标是降低客户输入负担：用户可以只说明“要做什么”，系统负责推断创作简报、受众假设、核心信息、视觉方向和逐页计划；客户只在计划与文件写入两个真正需要判断的节点介入。

- **两条入口**：`根据材料制作` 保留并升级现有 V1 的“已核验材料 -> 预检 -> 计划 -> 导出”链路；`从一句需求开始` 接收一句自然语言主题，可选材料但不强迫用户先写草稿。两条路径最终都进入同一份可阅读、可确认、带过期保护的逐页计划，不能把模型长回答直接写入 PPTX。
- **自动创意决策**：模型在受控 JSON 契约内输出标题、目的、受众、核心信息、三套内置视觉 token 之一、选型理由、逐页要点和最多六条素材检索词。新计划会把每条检索词绑定到封面或具体正文页的素材槽位，避免图片因下载失败或顺序变化贴到无关页面。没有材料时，计划必须明确标为“创作草案，关键事实待核验”，不得编造数字、客户案例、引用或来源；有材料时仍沿用 V1 的来源范围和预检。
- **低摩擦交互**：默认只展示一个意图输入框和可选附件；系统只在无法继续时提出少量关键追问。客户可以在导出前改用另一视觉方向或修改计划，但不需要先填写主题、风格、受众等长表单。PPT 工作台将使用独立子视图承载输入、计划、运行状态和交付结果，不挤压文档助手主页面。
- **视觉与模板**：V2.2 已将内置设计 token 落成可回读验证的封面、议程、图文陈述、信息卡、交付表格、总结与来源页等多种版式；模型仍只生成受控计划，版式由交付层决定。当前的三套视觉 token 仍是基础设计系统，不应包装成“海量模板”。第三方模板不能被网页随机下载后直接执行或复用：需要单独建立受控模板包、许可证记录、文件大小/MIME/宏与兼容性预检、版本元数据和显式选择，避免 `python-pptx` 对第三方母版、宏、图表或动画无法可靠保留的问题。
- **授权联网素材**：V2.2 已接入 Pexels 这一批准 Provider。计划阶段仍零联网；导出时只有用户勾选“导出时加入授权图片”并在确认框中批准，才会按最多六个已绑定页面的语义槽位查询图片。Provider 会以检索词与图片元数据作轻量重排，再只把成功结果嵌入对应页面；这降低了顺序错位，**但不是多模态语义验图，也不保证每张图库图完全符合叙事**。系统限制下载域名、大小与图片格式，记录提供方、素材 ID、检索词、作者、页面链接和许可证说明到 artifact 与来源页；未配置 Key、网络失败或无结果时安全降级为无外图的内置版式。Pexels Key 与 LLM Key 分开保存，模型不可读取。
- **多模态与图片生成**：只在供应商已确认具备图像生成能力、调用成本和内容安全策略都完成独立验收后接入。当前 Kimi/DeepSeek 的文本调用不能因为“支持多模态”就被假定能生成图片；V2 先预留受控视觉资产接口与来源审计字段。
- **权限与审计**：计划阶段不联网、不写文件；导出阶段必须用户确认。若启用授权素材，会在同一确认中单独列出联网读取权限。PPTX、素材来源、计划 ID、主题 token、回读验证和失败原因都写入原任务历史；原材料、原草稿及已存在交付物不被覆盖。
- **V2 MVP 明确不做**：自由 PPT 编辑器、任意网页/搜索引擎抓图、未审查的模板下载、企业品牌模板、没有可靠数据源的图表、PowerPoint 原生动画、音视频、联网事实检索、PPTX 反向编辑、PDF 导出和无材料情况下的事实正确性承诺。
- **验收标准**：一句主题可得到稳定的简报与 5 至 12 页计划；计划至少含封面、内容、总结和来源/事实核验页；模型 JSON 失败可进行一次无工具格式修复后安全降级；确认前零文件写入、零联网取图；确认后只在受控输出目录创建不重名 PPTX，并回读检查页数、标题、内容要点、唯一来源/核验页、视觉 token、表格文字和图片数量；授权素材启用时还要验证联网确认、来源元数据、图片嵌入和失败降级。

项目文档审查 v1 已完成：`POST /api/agents/document_agent/project-review/run` 与异步 `/start` 只接受一份用户明确选择的 workspace 项目材料，全文读取后按范围边界、验收标准、责任协作、节点计划、风险依赖和术语口径执行确定性检查；报告会区分“已识别”与“需关注”，每一项都有材料定位或明确的整份材料范围锚点。论文审查 v1 也已完成：`POST /api/agents/document_agent/paper-review/run` 以独立规则检查论文结构、参考文献区、图表提及、标题格式、正文引用映射与长段落可读性。两者都不调用模型、不修改原文、不写文件，扫描与规则结果进入标准任务/Tool 审计；Qt 在结果详情页的“审查”下拉入口打开各自独立阅读窗口，不挤压普通分析工作台。

配套架构决定：

- 原“报告助手”并入文档助手，不再单独作为正式内置 Agent；报告、方案书和演示文稿都是文档交付工作流。
- RAG 算法和索引降为平台级 Retrieval Service，由需要语义召回的 Agent 按需使用；2026-08-20 获批的 Knowledge Agent 只因具备独立资料生命周期、任务与权限而拥有客户页面，不能把每种检索算法再包装成 Agent。
- Evaluator/Verifier 是共用 Harness 验证层，不单独占一个应用页。转换任务检查文件可打开、非空和页数；PPT v1 回读检查页数、计划标题、内容页要点和唯一来源页；论文/正式文档按已公开的规则检查章节、引用映射和格式线索；问题显示在对应任务的结果和历史中。

### 当前只读理解 MVP 明确不做

- 不支持 Excel、PPT、图片 OCR、扫描件识别、密码绕过或复杂版式还原；PDF/DOCX 只提取可读取文本，不等同于 Office/PDF 编辑器。
- 不读取任意绝对路径、工作区外文件或未由平台授权的目录。
- 不修改、覆盖或删除原文，不执行 Shell，不联网，不安装插件，不访问数据库业务数据。
- 不在第一版建立向量库或长期知识库；精确定位先用 search/read，RAG 只在长文档语义召回确有收益时追加。
- 当前已实现的只读理解 MVP 不承担最终多 Agent 汇总；正式报告、方案书和演示文稿归入文档助手交付工作流，视觉素材按已确认 Provider 边界调用，跨 Agent 汇总由 Commander 负责。通用 Code Agent 已取消自研立项。
- 不把 Runtime 内部对象、API Key、绝对磁盘路径或权限实现细节发送给模型。

### 输入与输出建议

输入：

```json
{
  "task_goal": "从需求文档中提取功能、约束和待确认问题",
  "document_refs": ["assignment.md"],
  "query": "权限与审计",
  "output_mode": "requirements",
  "constraints": []
}
```

结构化输出 `document.context`：

```json
{
  "schema_version": "agentflow.document_context.v1",
  "documents": [],
  "summary": "",
  "brief_fields": [],
  "outline_sections": [],
  "draft_title": "",
  "draft_sections": [],
  "requirements": [],
  "comparisons": [],
  "constraints": [],
  "todos": [],
  "entities": [],
  "open_questions": [],
  "sources": [],
  "warnings": [],
  "missing_context": [],
  "confidence": "low"
}
```

`brief_fields[]` 使用稳定 key、字段值、`source_refs` 和置信度，当前内置 key 为主题、目的、范围、角色、交付物、节点和风险；`outline_sections[]` 包含章节 ID、标题、写作意图、关键要点、`source_refs` 和置信度，明确表示“待审阅大纲”而不是已交付文档；`draft_title` 与 `draft_sections[]` 包含草稿标题、章节 ID、标题、正文、`source_refs` 和置信度，明确表示“待审阅草稿”而非文件产物；`requirements[]` 至少包含稳定 ID、原始/归纳文本、类别、优先级、`source_refs` 和置信度。`sources[]` 使用受控相对路径和必要片段，不回显本机绝对路径。用户可读回答只展示最重要结论、来源和下一步。

### 模型、工具与上下文

- 模型策略：继承全局 `ModelGateway` 配置；第一版不绑定 DeepSeek，也不要求专属模型。无可用模型时使用确定性 mock，仅供离线/UI 验证，仍遵循同一 Tool 与来源契约。
- 模型调用：搜索/读取是 Tool；摘要、语义归纳和结构化抽取由通用 AgentRunner 的模型步骤完成，不把“模型总结”伪装成确定性文件 Tool。
- 上下文收束：单文档读取成功后关闭 Tool 面；其中关键信息卡、结构化大纲、Markdown 草稿预览和分章节创作预览仅公开 `document.read_text`，避免模型对固定字段或章节做无收益的逐项搜索。跨文档问答/整合/对比在 Runtime 确认所有选中材料均已连续读取到末尾后，于下一模型轮关闭 Tool 面。每页最多 48,000 字符，Tool 会返回 `next_start_char` 供长文档继续分页；每份材料最多预留两页，选满四份时总轮次上限为 10，其中最后一轮只允许修复最终 JSON、不能再读取或搜索。超过直接范围时改走连续分块压缩：每块最多 32,000 字符、每块最多两次结构化重试、每任务最多 12 块；全部分块成功后才标记全文覆盖，最终归并模型只能看到短摘要与原始行/页/段落来源。解析结果按文件 `mtime + size` 的 16 项 LRU 缓存复用，内容变化自动失效；解析和搜索均移出事件循环。该判断不依赖模型自觉，避免证据齐全后反复搜索耗尽预算，也不允许把文件开头片段伪装成全文。
- 可调用工具：`document.search_text`、`document.read_text`；可读取 workspace 文档目录的轻量列表，但文档导入由 Qt/平台入口负责。
- 默认权限：分析阶段仅 `file_read`，范围固定为受控 workspace；`file_write/network/shell/database` 全部关闭。草稿保存是用户在详情页主动触发、命名并确认的一次受控 `file_write`：范围固定为 `output/document_drafts/`，不允许模型自行触发、改路径或覆盖旧文件。
- 模型可见上下文：用户目标、候选文档元数据、必要搜索命中、受控读取片段、前轮结构化结果和允许公开的偏好。
- Runtime 本地上下文：绝对存储路径、数据库连接、权限决策、日志器、任务对象、模型凭据和原始审计记录。
- 记忆：MVP 只使用当前任务 State；不自动写长期用户记忆或向量库。

### Guardrails、停止条件与失败处理

- Input Guardrail：拒绝空目标、越界路径、不支持后缀和超限文件；候选多义时返回澄清问题。
- Tool Guardrail：对路径做 canonical containment 校验；限制单次读取大小、搜索命中数和返回字符数；Tool 结果按 schema 校验。精确搜索零命中只表示字面未命中，单文档会显式建议一次受控 `document.read_text` 回读并保留 search -> read 审计；没有任何来源时返回 `insufficient_context`，不把零命中断言成文档不存在。
- Output Guardrail：关键结论必须可关联来源；模型输出 JSON 需 Pydantic 校验；Runner 会尝试回复中的后续 JSON object，避免前置 schema 示例导致误判；首次无法解析或契约不通过时，最多进行一次不开放 Tool、不添加新事实的格式修复。仅当用户选择 `requirements`、Runtime 已有来源且修复后仍是 `model_output_invalid` 时，允许从原文中的中英文明确要求词（如“必须/不得”、`must/shall/required`）生成保守条目并标记降级。关键信息卡若已成功读取原文但 JSON 仍失效，则只可依据明确标题和字段标记生成保守字段卡；结构化大纲若已成功读取原文但 JSON 仍失效，则只可根据标题以及明确的范围、交付、计划和风险线索生成保守只读蓝图；两者均附复核警告。Markdown 草稿预览与分章节创作预览不允许规则降级生成正文：模型无法交付合法 JSON 时，任务必须如实失败并提示用户重试或缩小材料。分章节创作还必须验证源任务已完成、章节 ID 存在且结果恰好包含一个同 ID、同标题、带来源的章节；它不可覆盖源任务或任何 Markdown artifact。QA、摘要、跨文档问答、整合与对比均不适用这些降级。关键信息卡至少需有一项带来源字段，结构化大纲至少需有一个带来源章节，草稿预览至少需有带来源的标题和章节；只有用户显式确认后，保存节点才能把同一份已校验章节写入固定目录，且必须保留 Markdown 章节来源脚注、禁止覆盖并记录 artifact/log。跨文档问答和整合的 `answer_source_ids` 必须关联至少两份不同材料；整合后的兼容条目可保留多份来源，冲突或证据不足必须进入 `open_questions`，不得由模型自行裁定；对比项同样必须关联至少两份不同材料；不允许绝对路径和未读取文档中的虚构引用。
- 运行上限：单文档最多 4 个模型 turn、8 次工具调用；跨文档问答/整合/对比按材料数计算，最多 10 个模型 turn、8 次工具调用（每份最多两页后再收束，最后一轮仅可格式修复）；同类错误最多 2 次、单 Tool 默认 30 秒。达到上限明确终止并记录停止原因与格式修复次数。
- 停止原因：`completed`、`needs_clarification`、`insufficient_context`、`waiting_permission`、`failed`、`cancelled`、`max_turns_exceeded`、`budget_exhausted`；模型 HTTP 超时使用稳定的 `model_timeout`，保留已完成 Tool 审计并给出重试/更换模型建议。
- 典型失败码：`document_not_selected`、`ambiguous_document`、`unsupported_file_type`、`path_outside_workspace`、`file_not_found`、`file_too_large`、`decode_error`、`no_matches`、`insufficient_context`、`model_output_invalid`、`model_timeout`、`tool_timeout`、`cancelled`。
- 失败后给用户可执行建议，例如重新导入、选择具体文档、缩小关键词或补充目标；不无限自动重试。

### 文档工作台 v1 路线

产品定位：从“读取一份材料并给出带来源结论”升级为“读取资料、组织证据、协同专业 Agent、产出正式文档并维护版本”的文档工作台；它不是把所有写作、格式和知识库能力一次性塞进当前文档助手。

建议按下列顺序拆分可验收的小闭环：

1. **解析与证据扩展（已完成第一小闭环）**：PDF 与 DOCX 已接入确定性只读解析，PDF 来源保留页码、DOCX 来源保留段落或表格；限制为 10MB 原文件与 100 万提取字符，PDF 无可提取文本时明确提示 OCR 未启用，解析结果按 `mtime + size` 缓存。HTML、图片/OCR、章节语义和复杂版式仍未实现。
2. **多文档理解（已完成问答、整合与对比）**：明确选择 2 至 4 份材料后，可执行跨文档问答、可追溯整合或差异对比；所有材料连续读取，问答/整合结论和比较项均按各自契约保留跨文件来源。整合仅归并可兼容条目，冲突保留为待确认；长文档优先分块、搜索和摘要，不默认全量向量化。
3. **内置模板化抽取（已完成第一小闭环）**：关键信息卡按固定字段提取主题、目的、范围、角色、交付物、节点和风险，每项都有来源；它只读单份明确选择的材料，不开放逐字段搜索，也不提供自定义字段编辑。
4. **结构化大纲（已完成第一小闭环）**：基于单份明确选择的材料生成带来源的章节、写作意图和关键要点，供用户审阅。它不生成正文、不写文件，也不以常见模板虚构材料没有表达的章节。
5. **Markdown 草稿预览（已完成第一小闭环）**：基于单份明确选择的材料生成带来源标题与章节正文，供用户审阅；内容仅保存在任务结果中，不保存文件，且 JSON 失效时不自动补写正文。
6. **分章节创作预览（已完成第一小闭环）**：用户在已完成草稿详情中选择一个章节并输入创作指令，系统派生独立子任务、重新读取同一受控材料，只返回一个保留原章节 ID/标题且带来源的正文预览。它不改写原草稿、不保存文件、不做章节合并；失败时仍保留原草稿供用户审阅或另存。
7. **草稿事实核验（已完成第一小闭环）**：用户从已完成草稿详情发起只读核验，Runtime 恢复原草稿快照并重新读取相同受控材料，将“材料可支持的表述”和“待确认问题”分开显示。核验结果强制保留原草稿正文，不修改、保存、覆盖或合并任何章节；失败时原草稿详情不清空。
8. **正式文档创作与保存（已完成固定模板与合并预览基础）**：已核验草稿可按项目方案、PRD、会议纪要三个固定 schema 建立交付预览；模板重组只使用已有章节与来源，缺失章节不伪造内容，用户仍须确认另存 Markdown。两个同根、已核验完整草稿还可通过共同祖先进行三方章节合并，冲突必须逐项确认，结果仅创建独立预览。后续才讨论自由自定义模板、受众/语气字段和格式写入。
9. **本章只读审校（已完成第一小闭环）**：用户从草稿详情的“撰写本章”下拉操作选择“审校本章”，再选择章节和关注点。Runtime 只恢复原草稿快照与稳定章节 ID，重新读取原材料后返回问题级别、问题类型、原文片段、候选建议、理由和来源；原文片段必须属于该章节，建议不会自动应用、不创建文件、不修改草稿。失败时仍保留原详情。
10. **单建议修订预览（已完成第一小闭环）**：用户在本章审校结果中选择一条 `suggestion_id` 后，Runtime 从 SQLite 恢复审校快照，要求 `original_excerpt` 在目标章节中恰好出现一次，再做精确替换并建立独立任务。该任务不调用模型、不调用 Tool、不创建文件，详情页同时显示修改前/后和完整新草稿；原草稿、审校任务和既有 Markdown 均不变。用户若认可预览，仍必须走现有命名与二次确认，另存一个不覆盖旧文件的 Markdown 版本。
11. **多建议安全合并预览（已完成第一小闭环）**：用户可从同一份本章审校结果勾选 2 至 6 条建议；Runtime 要求每个原文片段唯一且彼此不重叠，按原文位置倒序建立独立新草稿，冲突直接拒绝。该任务零模型、零 Tool、零文件写入，原草稿/审校/已有 Markdown 均保持不变。
12. **版本链 v1、历史恢复与可见差异（已完成第一小闭环）**：所有可保存草稿快照都记录版本 ID、根草稿、直接父任务、变更类型和摘要；详情页可聚焦查看版本链，保存后的 Markdown 注释与 artifact 元数据保留同一身份。用户可从当前详情或历史任务选择已完成文档草稿，建立新的 `restored_preview` 子版本；服务端只复制受控快照，版本须继承根任务、直接父任务为被恢复快照，且不调用模型、Tool 或文件写入。派生版本可通过只读接口与直接父快照比较章节的未修改、修改、新增或删除状态，并在独立双栏窗口阅读两份正文。旧版本从不被原地覆盖或暗中回滚。
13. **受控可编辑修订**：再讨论逐条勾选后的命名版本、用户手动修改章节后的来源失效标记、重新核验、撤销/回退和可能的内置编辑器；不得把用户编辑的预览误当作已经通过材料核验或已修改原文。
14. **章节合并与版本策略（已完成第一小闭环）**：仅允许同一根草稿下、已核验的完整版本参与三方合并；服务端恢复共同祖先，未同时修改章节可自动保留，标题、正文、新增或删除冲突必须由用户逐项选择当前、候选或共同祖先版本。合并只创建独立 `merge_preview`，不接收自由正文、不覆盖旧任务/文件，也不把不同根任务文本伪装成已核验文档；自由编辑合并、自动冲突裁决和跨根合并仍不做。
15. **渲染与交付**：内容生成与 DOCX/PDF/HTML 渲染分离，渲染后执行预览检查；初期先交付 Markdown，再逐步增加可验证的格式适配器。

候选 Tool 按职责分层为 `parse_document`、`ocr_document`、`search_documents`、`extract_structured_data`、`compare_documents`、`create_outline`、`write_section`、`validate_facts`、`check_consistency`、`render_docx`、`render_pdf`、`preview_document`、`diff_versions`。其中读取/解析可沿用 `file_read`；任何改写、渲染落盘、导出、外部检索或跨 Agent 调用都必须单独定义 workspace 范围、权限确认、审计、失败恢复和验收标准。

明确暂缓：企业知识库/RAG、云文档连接器、多人审批、行业专业包、自动同步和生命周期管理。这些能力依赖更稳定的文件协议、隐私策略和版本模型，不能作为当前 Agent MVP 的隐性范围。

### 产品定位与不可替代性

目标用户是需要处理销售、运营、库存、问卷、项目统计或研究数据，但不熟悉公式、透视表和编程的办公用户。客户通常只愿意导入文件并说一句“看看销售趋势和区域差异”，系统应把这句话变成可审查的分析计划，再交付可以继续编辑的 Excel，而不是只返回一段模型总结。

普通聊天不能等价替代本 Agent，因为正式结果必须包含：

- 从客户真实数据计算出的指标、分组、排序、趋势和质量问题，禁止模型凭记忆补数；
- 可打开、可编辑、包含原生 Excel Table/Chart 的 `.xlsx` 产物；
- 源数据、清洗变更、指标口径、图表数据范围和结论之间的可追溯关系；
- 文件重新打开后的结构、数据和图表回读验证，以及任务历史中的产物与失败记录。

### MVP 输入范围

- 支持单个 `.xlsx` 或 `.csv`；不支持旧式 `.xls`、加密工作簿、宏文件、压缩包或任意数据库连接。
- 单文件最大 20MB；单次分析最多 100,000 行、100 列、10 个可见工作表。超过限制时先说明范围，不静默截断。
- MVP 一次只分析一张主数据表。Excel 会先列出工作表、行列数和候选表头，并自动推荐主表；判断不明确时只询问工作表或表头行，不要求客户填写复杂配置。
- CSV 首版支持 UTF-8、UTF-8-SIG、GB18030、带 BOM 或稳定字节序的 UTF-16，以及常见逗号/制表符/分号/竖线分隔；编码或分隔符无法稳定识别时停止并给出修复建议。
- 用户必填输入只有文件和一句可为空的分析目标。目标为空时执行“数据质量 + 基础概览”；目标简短时主动补齐合理视图，目标详细时把明确指标、筛选、分组和图表要求保存为硬合同。
- 高级选项采用渐进披露，只提供工作表、表头行、安全清洗策略和最多图表数；不向普通用户暴露模型温度、重试、DataFrame 表达式或代码。

建议的请求协议：

```json
{
  "file_ref": "workspace-data://sales.xlsx",
  "sheet_name": null,
  "header_row": null,
  "goal": "分析月度销售趋势、区域表现和产品结构",
  "cleaning_policy": "safe",
  "max_chart_count": 4
}
```

### 客户工作流

1. 导入 Excel/CSV，后端复制到受控数据工作区并记录文件指纹；Qt 只拿文件引用，不传任意绝对路径。
2. 确定性工具读取工作表和有限预览，生成字段类型、缺失值、重复行、唯一值、数值范围、日期范围和解析问题画像。
3. D2 以本地画像驱动的确定性规划器建立白名单与计算闭环；它只接收客户目标、列名、类型和聚合画像，绝不读取原始行。计算结束后可选的结论模型也只能接收已验证指标、有限聚合表和图表合同，返回严格 JSON 后仍必须验证引用 ID；不可用时回退本地结论。
4. Harness 校验计划引用的列、操作和图表是否存在且适用。只有会显著改变结论的歧义才询问客户，最多 1 至 2 个问题；其余情况自动继续。
5. 确定性执行器按白名单完成清洗、筛选、分组、聚合、排序和图表数据准备。模型不能生成 Python、公式或任意表达式交给 Runtime 执行。
  6. 结论层只依据已经计算并通过 schema 校验的指标、聚合表和图表合同生成简短结论。Tool 先构造有限的“事实底稿”（趋势、横向差异、连续曲线、汇总、质量问题及其表 ID），模型只能围绕它作解释；模型失败、超时、JSON 越界或遗漏数据锚点时回退同一份事实底稿，不能撤回已完成的数据计算和工作簿。
7. D3 已实现：渲染器先写临时 `.xlsx`，Verifier 重新打开并核对工作表、指标单元格、原生 Table/Chart、图表数量和文件完整性，通过后才移动到 `output/data_analysis/`；同名不会覆盖。
8. Qt 已提供“生成预览 -> 查看详情 -> 生成 PNG 看板或创建数据副本”的渐进交付入口，并在主工作台回显真实导出/验证状态；D4.1 已新增后台任务 API，先写历史、再发布阶段事件、最后登记历史 artifact。D4.2 已让 Qt 迁移到该入口，真实阶段结束或断流时补读终态，并通过仅在任务受理后显示的历史图标进入受控 artifact 打开入口。D4.3A 已支持从历史发起协作式取消：取消会恢复当前预览，不登记 artifact，且历史页明确引导客户回工作台重新确认，而不是重放不含客户全文目标的旧任务。

### 安全清洗与分析能力

`safe` 清洗允许自动执行并记录：去除表头首尾空白、为重复/空表头生成稳定名称、统一空字符串、按高置信度解析日期与数值、保留源值映射。任何转换都写入清洗日志和独立“清洗数据”工作表。

默认不自动删除重复行、不填补缺失值、不裁剪异常值、不合并类别、不修改源文件。需要排除无效行时，只在派生分析视图中应用并明确列出规则、影响行数和未参与统计的原因。

MVP 允许的确定性分析：

- 数据规模、字段类型、缺失率、重复率、唯一值、最小/最大值、均值、中位数、合计和分位数；
- 按一个或两个维度分组的计数、合计、均值、占比、排名和 Top/Bottom；
- 日期序列的日、周、月、季度或年聚合，以及环比变化；
- 类别对比、构成、数值分布和基础相关性提示；相关性只说明统计关联，不生成因果结论；
- 表格、柱状图、条形图、折线图、面积图、饼图和环形图。饼/环图只用于少量类别的真实构成关系；默认生成 2 至 4 个互补视图，客户明确数量和类型时按适用性形成硬合同。

### 输出协议与正式产物

结构化结果至少包含：

- `dataset_profile`：文件、工作表、行列数、字段类型和时间范围；
- `analysis_plan`：目标、维度、指标、筛选、清洗动作、表格和图表合同；
- `quality_findings`：级别、字段/行范围、影响、处理方式和受影响数量；
- `metrics`：稳定 ID、名称、数值、单位、口径和来源列/范围；
- `analysis_tables`：列定义、有限预览、完整工作簿位置和关联指标；
- `charts`：类型、标题、数据范围、关联指标、预览 artifact 和原生 Excel 对象状态；
- `insight`：只引用已计算 metric/table/chart ID 的醒目简短结论；模型不可用时必须有本地回退；
- `warnings`、`skipped_items`、`artifacts` 和 `verification`。

默认产物名为 `<源文件名>_分析结果_<时间>.xlsx`，保存到 `output/data_analysis/`，禁止覆盖。工作簿按实际内容包含：

- `分析说明`：用户目标、数据范围、口径、时间、警告和来源指纹；
- `数据概览`：字段画像和基础指标；
- `质量问题`：缺失、重复、解析和异常提示；
- `原始数据`：源数据的值副本，保留源文件不变；
- `清洗数据`：安全转换后的派生数据和变更说明；
- 一个或多个 `分析_...` 工作表，以及集中展示可编辑原生图表的 `图表` 工作表。

空内容不创建空工作表。长表启用冻结表头、筛选、合理列宽和色盲安全数据颜色；视觉格式服务于扫描和比较，不堆装饰。Qt 图表预览可由成熟绘图库生成静态预览，但 Excel 中的正式交付必须是绑定数据单元格的原生 Chart，不得用截图冒充可编辑图表。

### 模型、Tool 与 Runtime 边界

- 模型负责：理解简短目标、选择适用分析视图、把明确要求固化为计划合同、解释已验证指标。
- 确定性 Tool 负责：`data.inspect_file`、`data.profile_table`、`data.execute_plan`、`data.render_workbook`、`data.verify_workbook`。
- 计划只允许引用受控操作和现有列；未知列、任意代码、SQL、公式字符串和文件路径均由 schema/plan validator 拒绝。
- 首版采用现有 Native Runtime，不接 DeepSeek Harness、MCP、LangGraph 或 Shell。未来数据库连接、周期自动化或外部系统写入确有需求时，再按 H3/H4 门槛评估。
- 建议依赖为 `pandas + openpyxl`；图表预览若需要使用成熟静态绘图库。正式实现前锁定版本并评估 Windows 打包体积，不自行实现 DataFrame 或 Excel 引擎。
- 原始整表、单元格样本和客户敏感数据不写入普通日志或模型调用审计；任务历史只保留文件引用、结构摘要、指标结果、变更统计和产物元数据。

### 失败、降级与停止条件

- 空文件、无稳定表头、没有数据行、文件损坏、加密、超限或全部字段不可解析时不启动模型，直接返回原因、影响和处理建议。
- 模型计划引用未知列或不适用图表时最多修复 1 次；仍失败则降级为确定性的“数据质量 + 基础统计 + 类型适用图表”，并明确标为部分完成。
- 模型结论生成失败时仍交付已验证工作簿，状态为部分完成；不把模型文案失败误报成数据分析失败。
- 单个指标或图表失败只跳过该项并说明，不撤回其它合法结果。客户明确要求的硬合同若未满足，必须显示缺口，不能用其它图表悄悄顶替。
- 文件生成失败时保留结构化分析结果和诊断，不注册损坏 artifact；临时文件清理失败进入后台清理记录。
- 取消任务后停止后续模型/渲染步骤；同步 Excel 渲染不可强杀，故先记录 `cancelled`，后台返回安全提交点后清理未登记输出。已经完成的只读画像可以保留审计，但未验证或已取消的新文件不能交付。

### Qt 信息架构

复用现有左侧“数据洞察”导航，客户名称统一为“数据工作台”，不增加新的一级页面。稳定布局优先写入 `mainwindow.ui`。

- 主页面使用 `QStackedWidget` 表达“导入准备、运行中、结果摘要”三种状态，不把所有控件同时堆在一屏。
- 准备态以数据对象为中心：上方紧凑上下文条保留图标、能力边界和状态；中央大区域显示导入入口、工作表选择和有限行列预览；底部命令区只放一句目标和一个“开始分析”主按钮。
- 文件就绪后立即显示文件名、工作表、行列数和质量概览；高级设置通过侧边 Inspector 或独立弹层渐进披露，不用多排下拉框挤压数据预览。
- 运行态显示“导入检查 -> 数据画像 -> 计划 -> 计算 -> 生成工作簿 -> 回读验证”的真实阶段、耗时和取消操作；无法计算时不显示假百分比。
- 结果态只放结论摘要、质量问题数量、已生成表/图和主产物；完整内容进入独立可伸缩结果页。结果页使用“概览、数据质量、分析表、图表、交付文件”同级视图，表格用分页/按需模型，不把 100,000 行加载进 Qt 控件。
- 图表预览与 Excel 原生图表读取同一份已验证 chart contract；结果页不得重新让模型生成另一套数字。错误需持续显示原因、影响和下一步，不只弹出自动消失提示。
- 适配折叠后的全局导航和窄窗口；保证键盘焦点、40px 左右主要点击目标、文字状态、取消/重试和 50-100ms 的即时按钮反馈。

### MVP 明确不做

- 不做多文件合并、跨工作表 Join、VLOOKUP/XLOOKUP 修复、自由公式编写或宏/VBA。
- 不连接数据库、企业 SaaS、网页、MCP 或实时数据源，不自动联网补数。
- 不做预测、机器学习建模、因果分析、金融投资结论、自动经营决策或专业统计检验平台。
- 不覆盖或修改源文件，不自动删除行、填补缺失值或处理异常值。
- 不把长篇报告和 PPT 制作复制进数据 Agent；它交付结构化分析和 Excel，正式叙事交给文档助手。
- 不提供任意 Python/SQL 执行框、插件脚本或模型生成代码运行能力。

### MVP 验收标准

- 客户导入一个含中文字段、日期、类别、金额、缺失值和重复行的 Excel/CSV，只输入一句目标即可完成任务，不需配置公式或列映射。
- 源文件保持字节不变；输出只写入 `output/data_analysis/`，同名不覆盖，失败不留下可误认成完成品的文件。
- 输出工作簿可重新打开，包含真实数据画像、质量问题、清洗记录、分析表和适用的原生 Excel Chart；图表数据范围和指标单元格可回读匹配。
- 所有数字均可由输入数据和受控操作重新计算；模型不能提供来源不明的数值，结论只能引用已验证的 metric/table/chart ID。
- 客户明确要求的维度、指标和适用图表会进入硬合同；无法满足时在执行前澄清或在结果中明确列出缺口。
- 模型规划失败时仍能交付基础分析；模型结论失败时仍能交付工作簿；单图失败不撤回其它分析。
- Qt 主线程在导入、画像、模型、计算、渲染和验证期间保持可交互，100,000 行不直接塞入 UI；按钮在 100ms 内进入提交状态。
- 历史任务能复盘阶段、耗时、工具、警告、清洗统计、图表合同、验证结果和 artifact，但不保存原始整表或敏感单元格样本。
- 离线回归覆盖成功、编码、空表、重复表头、超限、计划未知列、模型失败、部分图表失败、同名保护、取消和损坏文件；真实模型验收只使用合成数据并输出脱敏统计。

### 实现顺序与后续扩展

正式开始后按四个可验收小闭环推进：
