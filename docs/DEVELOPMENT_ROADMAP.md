# AgentFlow 分阶段开发路线

最后更新：2026-08-26

本文用于约束 AgentFlow 后续开发顺序。`AgentFlow_初版规划.md` 是长期愿景，`docs/PROJECT_STATUS.md` 是当前状态，本文件负责把愿景拆成可交付阶段，防止 MVP、商业版、插件市场、RAG、视觉和打包目标混在一起导致失控。

## 总体判断

AgentFlow 可以做完整，但必须分三层推进：

- MVP：跑通本地多 Agent 工作流最小闭环，能稳定演示“需求 -> 规划 -> 执行 -> 产物 -> 日志 -> 历史”。
- Beta：加入真实文件工具、真实 Agent Runtime、基础打包和更完整 Qt 交互，变成自己日常可用的软件。
- 长期版：插件市场、视觉/音视频、复杂沙箱、多用户/企业化和商业安装包。知识库已由用户明确批准提前进入阶段 5K，不再笼统留在长期版。

短期不要追求真正“所有文件压成一个单 exe”。更稳妥的目标是：用户看到一个启动入口 `AgentFlow.exe`，内部可以带后端 exe、agents、data、config、logs。真正单文件 exe 等核心能力稳定后再评估。

## 当前规划的问题

当前方向是对的，但存在这些风险：

- 范围过大：初版规划把 MVP、插件市场、视觉、RAG、商业化和多平台都写进去了，容易误以为要同时做。
- 后端协议快于前端体验：后端已有 metrics、runtime-state、artifacts、tool-calls 和执行入口，Qt 历史页已补当前选中任务的轻量自动刷新和受控产物工具条，但还需要继续补运行中反馈和更细的预览异常提示。
- Runtime 真实执行范围还很窄：当前只允许安全内置工具读取受控 workspace、写入受控 outputs；Shell、用户代码、联网和插件仍未开放。
- 数据库还没有迁移系统：目前用 `CREATE TABLE IF NOT EXISTS` 够用，但字段稳定后需要轻量 schema version。
- 打包目标需要重新定义：先做“单入口应用/便携目录/安装包”，不要过早追求真正单文件。
- 长期依赖要按客户闭环引入：Redis、MCP、YOLO 和无明确场景的复杂框架仍应延后；向量库与 RAG 因本地知识库方案已获明确批准，只允许按阶段 5K 的 K0 技术试验和 K1-K5 门槛推进。LangGraph / LangChain 仍通过适配边界按真实复杂度接入。
- 检索路线要提前定清楚：后续知识库阶段不是“纯 RAG 替代一切”，而是 agentic search first。代码和项目文件先用 grep/ripgrep/glob/read file 按需检索，RAG 只补语义理解、长文档问答和跨文档归纳。
- Agent 名称已经先于 Agent Runtime 出现：当前 manifest、Node Contract 和 Runtime action 仍保留 Document / Code / Report 等历史名称，但 Registry 元数据、协议占位和页面可见均不等于产品立项或 Runtime 就绪。阶段 5 必须把兼容资产、演示动作和正式 Agent 分开描述。

## 2026-07-10 架构复审结论

结合当前仓库、Codex 官方 Agent/Codex 工程文档和 `D:\CC\claude-code-main` 的实现及其自审报告，阶段 5 做如下校准：

- 先做一个聚焦 Agent。新增 Agent 的依据是职责所有权、工具面、权限策略、模型策略或输出契约发生实质变化，不按页面或营销名称机械拆分。
- 内置 Agent 采用共享 `AgentRunner`，由 Agent Definition 提供指令、模型策略、工具白名单、上下文策略、Guardrails、停止条件和输出 schema。确定性文件读取、搜索、写入仍是 Tool，不复制 Agent 循环。
- Commander 第一版采用 manager 模式：始终保有任务、计划和最终回复所有权，把 Document 等专业 Agent 当作有边界的能力调用；handoff 等到确有“专家接管会话”需求时再引入。
- 模型可见上下文与 Runtime 本地上下文分开。凭据、数据库对象、权限状态和内部路径只留在 Runtime；模型所需事实通过输入、检索或脱敏工具结果提供。
- 人工审批建模为同一次 run 的 interruption：保存待审批调用与可恢复状态，批准/拒绝后继续原任务，不新建一条割裂的执行链。
- Sandbox 决定“技术上能触碰什么”，Approval Policy 决定“何时必须询问”，两者必须独立建模；Guardrail 还要分别覆盖输入、工具参数/结果和最终输出。
- 多 Agent 并发不是阶段 5 首要目标。以后启用并发时，预算需要预留/原子扣减，journal 需要稳定事件 ID 和确定顺序，单分支错误不能静默吞掉。
- 后台任务必须主动发终态通知。只更新数据库或隐藏面板而不通知完成/失败，视为用户体验缺陷。
- `D:\CC\claude-code-main` 是第三方复原/扩展工程，不是官方源码。它适合提供架构线索和反例，但不能作为事实权威，也不直接复制其 JS workflow 沙箱、权限或路径处理实现。
- OpenAI Agents SDK 当前也只作官方模式参考，不直接成为核心依赖；多供应商 ModelGateway、AgentFlow 自己的 task/state/permission/updates 协议必须保持稳定，未来框架只能作为可替换 adapter。

## 硬性开发规则

- 每轮只推进一个阶段内的小闭环，不跨阶段乱加能力。
- 新增后端协议必须有 `verify_backend.py` 覆盖。
- 新增 Qt 可视结构优先改 `mainwindow.ui`，不能破坏原有图标、渐变背景和页面层级。
- 真实文件写入、Shell、联网、插件安装必须先走权限请求和审计记录。
- PPT 的公开资料参考不等同于结构化数据源：百科/搜索摘要只能作为来源页和人工核验线索，不能直接驱动统计图表、关键数字或模型事实结论。主创作规划与专用研究规划按 `docs/PPT_RESEARCH_DATA_DESIGN.md` 职责隔离，后者只生成通用研究蓝图；当前实际数值读取开放 World Bank 快捷 Provider 与第一版 ResearchGateway。ResearchGateway 必须经用户确认、受控搜索 adapter（DeepSeek 原生搜索或 Tavily 清洗正文）、受限来源读取、二次抽取和一致性 Verifier 后才能交付；任何不匹配、数据不足或接口失败都跳过，不能猜测或混用年份。真实通用主题验收未通过前，不扩大到任意来源或宣称稳定。
- 不把供应商逻辑写进 Agent / Workflow / Tool 层，统一走 `ModelGateway`。
- 每个阶段完成后更新 `docs/PROJECT_STATUS.md`；路线变化再更新 `README.md` 和本文。

## Agent 工程资料吸收后的路线校准

`docs/飞书文档.txt` 里的 LangChain / LangGraph 内容对方法论有价值，也和初版技术栈方向一致。现阶段的路线是：保留自研 FastAPI + SQLite + Workflow Runtime，把其中的成熟思想先转成 AgentFlow 自己的协议和文档；阶段 5/6 之后再评估 LangGraph 接入到复杂编排、并行、子图或插件工作流中。

立即吸收：

- State / Node / Graph 思维：阶段 5 开始，每个内置 Agent 步骤都要明确输入、输出、状态写入和失败策略。
- 结构化工具协议：工具定义、参数、返回、错误、权限都走 schema，不靠模型自由发挥。
- Human In The Loop：敏感 Action 节点继续走权限审计，后续再扩展为批准、拒绝、编辑、补充信息等更细动作。
- updates 事件流：Qt 不只看最终结果，还要逐步展示计划、工具调用、权限中断、产物和评估。
- Evaluator/Verifier 作为所有 Agent 共用的 Harness 验证层：按产物类型做有限次数的质量检查和修正，把问题展示在原任务中，不单独包装成 Agent 或应用页，也不允许无限循环。

暂缓吸收：

- LangGraph / LangChain 作为核心运行时依赖暂缓；等阶段 5/6 稳定后，按复杂分支、并行、子图、人工中断恢复和插件工作流的需求做接入评估。
- LangSmith 暂缓；先用本地 SQLite、日志、验证脚本和后续评估页承担可观测性。
- Redis、向量库、外部搜索工具和复杂 RAG 仍放在 MVP 之后；进入知识库阶段时优先做 `RetrievalRouter` 和即时搜索工具，而不是先把全部内容向量化。

## 阶段 4A：Dry-run Harness 基线

状态：已达到阶段出口。

目标：

- `workflow_plan`、计划校验、dry-run、状态查询、日志查询、SQLite 持久化。
- 权限请求/决策、artifacts、tool-calls、metrics、runtime-state。
- Qt 历史页能看到任务列表、步骤、日志和权限确认。

验收标准：

- `python scripts\verify_backend.py` 通过。
- 清空内存缓存后任务可从 SQLite 恢复。
- Qt 历史页不破坏原有视觉，权限区不遮挡摘要。

## 阶段 4B：真实 Runtime 最小执行器

状态：已达到阶段出口。后端闭环和 Qt 历史页验收面已经足以支撑首个正式小 Agent；后续只按阶段 5 的真实需求修补，不再把 4B 当作无限扩建的平台阶段。

目标：

- 引入真实 Runtime 执行壳，但先只执行安全内置工具。已完成当前范围。
- 任务状态按 `pending -> running -> waiting_permission -> completed/failed/cancelled` 转移。已覆盖等待权限、完成和取消。
- 工具调用从 `simulated` 变成可更新的 `running/completed/failed/blocked`。已覆盖 `pending_permission/completed/skipped/blocked/failed`。
- 支持取消、重试、权限等待、失败计数、最多两次重试和超时。已覆盖取消、权限等待、结构化失败、重试边界字段、超时中断和自动重试循环。

建议先做的工具：

- `document.read_text`：只读 txt / markdown。
- `artifact.write_markdown_draft`：只写入受控 outputs 目录。
- `report.compose_markdown`：基于已有步骤输出生成 Markdown。

不做：

- 不执行任意 Shell。
- 不跑用户代码。
- 不装插件。
- 不接复杂 RAG。

验收标准：

- 后端离线验证覆盖成功、权限等待、权限拒绝、取消、受控产物、结构化失败、自动重试、超时和工具边界。
- 所有真实文件产物只落到受控输出目录。
- Qt 至少能通过历史页看到真实产物、工具状态和运行指标。

难度：中高。这里是从“协议壳”进入“真实可用”的关键关口。

## 阶段 5：内置 Agent MVP

状态：**首个正式 Agent 已完成；阶段 5 尚未整体结束。** 文档助手的直接入口、真实模型 Tool Calling 验收、单文档理解、内置关键信息卡、结构化大纲、Markdown 草稿预览/确认保存、分章节创作预览、草稿事实核验、本章只读审校、单建议及多建议修订预览、跨文档问答/整合/对比、长文档上下文压缩、Commander manager 委派均已完成。已实现通用 AgentRunner、跨 provider Tool Calls 适配、`runtime_ready/health/maturity`、受控 workspace Tool、结构化来源映射、父子任务审计和 Qt 页面。单文档读取后会关闭 Tool 获取阶段；关键信息卡、结构化大纲、Markdown 草稿预览和分章节创作预览只暴露一次受控全文读取，前者按固定字段输出来源事实，大纲输出带来源的章节、写作意图和关键要点，草稿预览输出带来源的标题与章节正文，分章节预览则从已完成草稿中选择一章、重新读取同一受控材料、仅返回一个保留原章节身份且带来源的派生结果。审校建议修订预览只从已完成审校任务恢复稳定 suggestion ID：单条模式要求原文片段唯一；批量模式额外要求 2 至 6 条片段均唯一且互不重叠，并按原文位置倒序替换，拒绝任何猜测式合并。两者均不调用模型或 Tool、不改写旧稿，用户确认后仍只能另存新 Markdown。用户在详情页命名并确认后，后端只会将已验证草稿以 UTF-8 Markdown 写入项目根 `output/document_drafts/`，默认禁止覆盖同名文件，并把受控产物与保存事件追加到原任务历史。跨文档任务支持 2 至 4 份材料，从文件开头连续分页读取，每页最多 48,000 字符，Runtime 确认材料读到末尾后动态关闭下一轮 Tool 面，强制模型收束为结构化结果并绑定跨文件来源。跨文档问答和整合的 answer 必须直接引用至少两份材料；整合只归并可兼容内容，冲突列为待确认；对比项则必须关联不同文件来源。超过直接上下文范围时改走连续分块摘要与最终归并，最多 12 块并显式报告预算不足；Code 尚未进入正式实现，遗留 Report 占位不再作为独立产品方向。

首个真实文件交付闭环：**PDF 整理基础版已完成。** 它不是 LLM 按钮，而是文档助手调用的确定性 Tool，支持受控 PDF 的合并、提取、旋转、删除。用户在 Qt 独立工作区明确选择文件、范围并二次确认；系统只在 `output/document_processing/` 生成新副本，重新打开验证文件与页数，并将 step、实时事件、artifact、Tool 审计和失败原因写回统一任务历史。原件不覆盖、不删除；PDF 之外的格式写入、OCR、压缩和批量处理仍未进入范围。

### 阶段 5A：通用 Agent Runner

目标：

- 定义可验证的 Agent Definition：身份/指令、模型策略、工具白名单、权限、模型上下文策略、Runtime 上下文、输入输出 schema、Guardrails、最大轮次和停止原因。
- 为 Agent Registry 增加独立的 `runtime_ready/health/maturity` 语义；`enabled` 只代表允许展示/使用，不能替代实现就绪判断，Commander 只路由可执行 Agent。
- 在 `ModelGateway` 后增加统一的结构化 Tool Calls 能力，兼容 OpenAI-compatible 与 Anthropic Messages；不把供应商协议写进 Agent。
- 实现有硬上限的通用循环：模型调用 -> 参数校验 -> 权限/Guardrail -> Tool -> 结构化结果 -> 下一轮，直到完成、等待确认、失败、取消或预算耗尽。
- 把模型事件、工具事件、审批 interruption、终态和错误写入现有 task/step/tool_call/updates，不另建一套不可见状态。
- 先只允许低风险只读工具。动态导入第三方 `agent.py`、任意 Shell 和用户脚本不属于 5A。

验收标准：

- runner 能区分 `completed`、`waiting_permission`、`failed`、`cancelled`、`budget_exhausted` 和 `max_turns_exceeded`。
- Runtime 本地上下文不会被默认序列化给模型。
- 同一工具同类失败、审批拒绝和最大轮次都有明确停止条件。
- 一条 run trace 能关联模型调用、工具调用、参数校验、权限决策和最终结果。

### 阶段 5B：文档助手纵向闭环

状态：**只读文档理解 MVP 已完成，含内置关键信息卡、结构化大纲、Markdown 草稿预览/确认保存、分章节创作预览、草稿事实核验、本章只读审校、单建议及多建议修订预览、版本链 v1、历史快照恢复预览、跨文档问答/整合/对比、长文档上下文压缩和 PDF/DOCX 解析扩展。** 直接入口、真实模型验收、受控来源、任务历史、Commander manager 委派和实时阶段事件均复用同一 `AgentRunner` / `agent.document_agent.analyze` 链路。单文档固定输出只开放一次 `document.read_text`：字段卡提取七类明确事实，大纲提供带来源的章节蓝图，草稿预览生成带来源标题和章节正文；分章节预览从已完成草稿中选择一个章节，以派生任务重新读取相同受控材料后，仅返回保留原章节 ID/标题的带来源结果。审校建议修订预览不调用模型、不接受客户端正文或路径：单条模式只按 suggestion ID 精确替换唯一原文片段；批量模式选择 2 至 6 条 suggestion ID，要求每个片段唯一且相互不重叠，再按原文位置倒序应用。两种模式都展示前后差异并保留完整新草稿，不改写源草稿或已保存文件，确认后仍只允许通过保存确认另存。每个可保存快照会额外记录版本 ID、根草稿、直接父任务、类型和变更摘要，并将该身份写入详情、Markdown 注释和 artifact 元数据；用户可从详情或历史任务把任一已完成快照恢复为新的独立版本，恢复过程只复制 SQLite 中的 Pydantic 快照、再次核对版本身份、零模型/零 Tool/零文件写入，旧版本绝不被原地覆盖。保存不调用模型、不接受任意本机路径，只会将已验证章节以 UTF-8 Markdown 写入 `output/document_drafts/`，拒绝覆盖同名文件并记录 artifact 与日志。字段卡与大纲可在严格条件下生成保守结果；草稿和分章节预览在 JSON 无效时必须如实失败，绝不规则补写正文。跨文档问答、整合和对比必须显式选择 2 至 4 份材料，连续读取、绑定跨文件来源，并在超出直接范围时采用连续分块摘要与最终归并。PDF 仅处理可提取文本并保留页码，DOCX 保留段落/表格定位；解析缓存按 `mtime + size` 自动失效且不阻塞事件循环。已完成的文件交付包括 PDF 整理基础版和固定模板的项目方案 PPT v1；OCR、Excel、自由 PPT 编辑、可编辑版本链、自定义企业模板及其他格式写入交付仍需与用户确认范围后再进入实现。

补充：版本链现已提供“当前版本 vs 直接父版本”的双栏差异阅读。该接口只读取 SQLite 中已验证快照，明确标出章节未修改、修改、新增或删除，不创建任务、不调用模型或 Tool、不读取 workspace，也不写入文件；Qt 从版本菜单打开独立可伸缩窗口，避免把双份正文挤进结果卡。

### 阶段 5C：后续专业 Agent

- 文档助手的产品方向调整为文件转换与处理、智能文档/PPT 制作、文档审查；三个方向已获认可，但每个具体 MVP 仍须逐项讨论、确认后实现。
- 原 Report Agent 并入 Document Agent，不再作为独立专业 Agent；报告、方案书和演示文稿属于正式文档交付工作流。
- 2026-08-14 已取消自研通用代码工坊 Agent：不以复刻 Codex、Claude Code 或 Cursor 为产品路线，也不再安排“代码理解、草稿、审查”MVP。既有 manifest、Node Contract、命令策略和 UI 占位属于历史兼容或平台资产，不代表待开发 Agent。
- 未来若客户确有代码工作流需求，优先评估受控接入成熟外部代码 Agent；该能力属于平台 Adapter，必须另行确认目录范围、命令权限、联网、审计、产物和责任边界。
- RAG 算法和索引作为平台 Retrieval Service 按需提供，Evaluator/Verifier 作为共用验证层按产物执行检查；获批的 Knowledge Agent 只持有资料生命周期、客户问答和深度任务，不复制底层检索能力。
- Commander 在每个专业 Agent 真正可用后再扩大路由范围，不能规划系统尚未兑现的能力。
- 新专业 Agent 一次只讨论一个。先评估客户痛点、不可被普通聊天直接替代的交付物、实现可行性、工具/权限、商业属性、明确不做和验收标准；用户确认后才写正式规格和实现。

MVP 演示：

```text
用户输入目标或材料
-> Commander 规划
-> 已批准的专业 Agent 使用受控 Tool / Runtime 完成任务
-> 共用 Verifier 回读文件、数据或状态变化
-> Qt 展示进度、权限、可用产物、问题和历史
```

验收标准：

- 不依赖人工改数据库或手动复制文件。
- 输出目录有与当前专业任务对应、可打开且经过回读验证的正式产物。
- 用户能在 Qt 里看到任务是否完成、失败在哪里、产物是什么。

难度：中高。主要难点从“多写几个 Agent 类”改为稳定的模型工具循环、上下文边界、暂停恢复、可观察性和可验证用户结果。

### 阶段 5E：总指挥 Agent MVP

状态：**C0、C1、C2 初版、C3 的计划版本和执行治理，以及 C4 的知识库只读窄委派均已完成：材料绑定、范围可见确认、文档真实委派、数据工作台诚实交接、资料库可信问答委派、父任务汇总、用户可控的最小长期记忆、不可变计划快照、后台 Runtime、协作式暂停/继续/取消和阶段事件流均可审计；Qt 已提供执行前的版本审阅与目标修订 Inspector、知识库显式委派入口，以及历史页的执行控制，但尚未构成完整总指挥产品。** 本阶段的目标不是再造一个通用聊天模型，而是完成 AgentFlow 的任务控制平面。

总指挥 MVP 必须同时认识文档助手和数据工作台，并根据具体 action 的准入状态决定“可执行委派”还是“解释并引导”。文档助手的已验收 action 可以成为首条真实委派链；数据工作台已通过 D5.4 与 R5.4A/B 的最小输入映射、数据最小化和写入验证准入，可对一份已绑定数据集执行只读分析，并在确认后交付 PNG、分析工作簿或字段加工副本；R5.4C 首版还支持两份明确绑定数据的受控 left/inner 关联副本。复杂多表关系、任意表达式和其它写入能力仍不自动开放。

实施顺序：

1. **C0 协议与准入（已完成）**：已补齐 Agent action 的输入类型、预期产物、风险/确认、Verifier、恢复语义与 `runtime_ready` 准入目录；已清理旧 Code/Report 占位能力的客户可执行路由。
2. **C1 原生计划闭环（已完成初版）**：已完成“任务输入 -> 显式材料绑定 -> 结构化计划 -> 范围可见的用户确认 -> 文档真实委派 / 单数据集只读委派或数据工作台诚实交接 -> 父任务汇总”的首条闭环。更细的流式执行体验、计划修改和暂停/恢复治理归入后续 C3；规划模型默认走高质量优先策略，但始终由多供应商 `ModelGateway` 选择，不能锁定某个模型或 Harness。
3. **C2 长期记忆（初版已完成）**：会话状态继续由任务/计划/事件表保存；长期层已用 AgentFlow SQLite 落地用户偏好、项目约束和可复用经验三类显式确认记录。用户可在系统设置查看、新建、编辑、关闭、删除或明确清空；默认关闭，开启后只按标题/标签/摘要检索最多三条相关短事实。不得保存 API Key、原始表格行、完整私密材料、绝对路径或未经授权的模型推测。

## 阶段 6：Qt 前端补齐 MVP 体验

### 前端体验验收基线

`docs/前端设计可借鉴文档.md` 是前端体验的完整参考；以下是每次 Qt 页面、交互或视觉改动都应执行的 P0 检查，避免只追求控件数量或局部好看：

- 信息架构：以用户当前任务和对象为中心。长结果、来源、审计、配置不堆进一张卡片，优先采用“工作台负责输入与运行，详情页/Inspector 负责聚焦阅读与复核”的渐进披露结构。
- 状态与 AI 信任：空闲、运行、等待输入或权限、成功、部分完成、失败均有文字状态、影响说明和下一步；结果附来源或 Tool 证据。颜色只作辅助，不得成为唯一状态信息。
- 控件与可达性：一个区域通常只有一个主操作；禁用操作说明原因；常用操作支持键盘焦点和 Tooltip；长文本、窄窗口、缩放后不能重叠或裁切关键内容。
- 性能与动效：网络、文件、模型和流式结果不阻塞 Qt 主线程；首先在 50–100ms 内反馈按钮状态；没有可计算进度时显示真实阶段。动效仅用于页面/面板关系、成功或错误反馈，必须可打断且不制造虚假进度。
- 视觉一致性：沿用 AgentFlow 的标题层级、图标、渐变识别区、语义状态色与 4px/8px 留白节奏；不把全页面做成玻璃卡片，不为“高级感”堆强阴影、渐变或无意义动效。

大型新页面先在本基线下完成信息架构和状态闭环，再考虑可记忆面板、命令面板、密度模式、共享元素过渡等 P1 增强；这些能力需配合可见运行与性能验收逐项加入。

目标：

- 历史页继续完善 runtime-state、metrics、tool-calls、artifacts 的运行中反馈、预览异常提示和多类型产物呈现。
- 调度台展示计划、updates 事件流、执行状态和错误原因更清楚。
- 模型页支持 per-agent 模型覆盖的最小版本。
