## 1. 产品定位

客户侧名称统一为“知识库”，内部实现分成两个层次：

- `Knowledge Retrieval Service`：平台级检索底座，负责解析、分块、索引、混合召回、重排、来源定位和检索诊断，供总指挥、文档助手及未来专业 Agent 复用。
- `Knowledge Agent`：面向客户持有知识库生命周期、可信问答、跨文档分析和深度任务。它只能通过受控 Retrieval Service 操作资料，不直接接触向量数据库内部对象。

知识库不应退化成“上传 PDF 后聊天”。普通 LLM 能完成泛化问答，但不能可靠完成本地资料的持续入库、增量更新、精确引用、删除失效、跨文档覆盖审计和可恢复长任务；这些才是本功能不可替代的产品价值。

现有“RAG 默认是平台 Retrieval 服务”的规则继续成立。知识库之所以可以拥有客户页面和 Agent 身份，是因为它已经具备独立的资料生命周期、工具面、权限边界、任务状态和交付契约；底层 RAG 算法本身仍不包装成另一个 Agent。

## 2. 目标客户与真实场景

- 学生和研究人员：管理课程、论文与研究资料，跨材料查证观点并定位出处。
- 项目成员：查询需求、会议纪要、方案和历史决策，比较版本或查找冲突。
- 办公与运营人员：管理制度、流程、产品资料和内部手册，生成可追溯专题说明。
- 小团队和个人：在本机维护私有资料，不依赖外部 SaaS 托管完整原文。

MVP 优先解决以下任务：

1. 创建资料库，导入、更新和删除本地文档。
2. 对明确选择的一个或多个资料库进行带引用问答。
3. 精确查找编号、名称、术语、条款和原文位置。
4. 比较多份材料的共识、差异、冲突和缺失项。
5. 对整份或整库资料执行摘要、专题归纳和风险审查，并交付可复盘报告。

## 3. 产品边界

### 3.1 MVP 要做

- 支持 TXT、Markdown、PDF 和 DOCX；复用现有已验证解析器和来源锚点协议。
- 支持知识库、文档、版本、索引状态、失败原因和更新时间管理。
- 使用内容哈希识别重复与变更，只重建发生变化的派生索引。
- 使用精确/关键词检索与向量检索组成 Hybrid Retrieval。
- 使用父子分片、RRF 融合、去重和可选 Reranker 精排。
- 回答中的关键事实必须关联来源，资料不足时必须拒绝补写。
- 深度任务使用分批 Map-Reduce、SQLite checkpoint 和可恢复阶段事件。
- 任务、工具、检索模式、引用、耗时、成本和失败原因进入现有历史与审计。

### 3.2 MVP 明确不做

- 不做扫描件 OCR、手写识别或复杂版面复原。
- 不做网页爬虫、自动同步、云盘、数据库或企业 SaaS 连接器。
- 不做多人协作、成员 ACL、企业组织权限和跨设备同步。
- 不做知识图谱、自动本体构建或全自动事实合并。
- 不修改、覆盖或删除用户原始文件；知识库删除只清理受控副本和派生索引。
- 不把完整聊天历史、原始表格行、API Key 或未经确认的模型推测写入知识库。
- 不默认向量化代码仓库、日志、配置和强结构数据；这些内容仍优先即时精确检索。
- 不为每个专业 Agent 复制一套独立向量库。
- 不无条件执行查询重写、HyDE、Rerank 或原生长窗口。

## 4. 客户工作流

### 4.1 资料库

1. 客户创建资料库并选择受控文件导入。
2. 后端复制到知识库受控目录，计算哈希并建立文档版本。
3. 解析器输出结构化段落、标题路径、页码/段落/行号和表格线索。
4. Index Job 在后台生成父块、子块、关键词索引和向量索引。
5. Qt 显示“排队、解析、索引、就绪、部分失败、失败”真实状态；失败文件可单独重试。
6. 更新文件建立新版本并原子切换活动索引；旧版本在切换成功前仍可查询。
7. 删除资料时同步失效文档记录、关键词索引、向量、缓存和受控副本，并留下脱敏审计。

### 4.2 可信问答

1. 客户选择一个或多个资料库并输入自然语言问题。
2. `RetrievalRouter` 根据问题类型选择不检索、精确检索、混合检索、多跳检索或深度任务。
3. 检索服务返回受控证据包，而不是把数据库对象或任意长原文交给模型。
4. 模型只依据证据包生成回答；输出契约要求声明使用的 `source_id`。
5. Verifier 检查引用存在、来源仍属于活动版本、关键结论有证据。
6. Qt 流式显示回答阶段，完整正文位于主阅读区，来源位于可折叠侧栏并可跳转原文。

### 4.3 深度任务

跨文档比较、整库摘要、专题报告、逻辑一致性或风险审查进入独立后台任务：

- Map 节点按父章节或文档分批处理，输出固定 schema、来源和覆盖范围。
- 并发数受全局预算限制，默认使用小规模有限并行，不一次启动全部文档。
- Reduce 节点分层合并、去重并保留冲突，不把无来源子结论提升为最终事实。
- 每批状态写入 SQLite checkpoint；暂停、取消和失败恢复沿用现有 Runtime 安全边界。
- 最终结果包含报告、来源、覆盖范围、失败分片和证据不足项；只有用户确认后才保存正式文件。

## 5. 检索架构

### 5.1 RetrievalRouter

路由优先采用确定性规则，只有分类存在真实歧义时才调用轻量模型：

| 查询类型 | 默认路线 |
| --- | --- |
| 问候、界面帮助、与资料无关的普通交流 | 不检索 |
| 引号原文、编号、ID、专有名词、文件名、条款 | 精确/关键词检索优先 |
| 同义表达、概念解释、模糊问题 | Hybrid Retrieval |
| 比较、因果链、多对象或多跳问题 | 最多拆分 3 个子查询后 Hybrid Retrieval |
| 全文摘要、整库审查、全局一致性 | Map-Reduce 深度任务 |

查询重写仅在口语化、上下文指代或首次召回不足时触发，最多一次。HyDE 容易把模型假设带入召回，MVP 不默认启用，只保留为离线评估实验。

### 5.2 父子文档分片

- 父块负责保留完整章节、标题路径、页码范围、表格上下文和邻接关系。
- 子块负责精确匹配，初始实验范围为约 200-500 tokens。
- 相邻子块初始重叠约 10%-15%，最终值按文档类型和评估集确定。
- Markdown/DOCX 优先按标题结构切分，PDF 优先按页、段落和可恢复结构切分。
- 子块命中后按证据预算召回父块或有限邻接片段，避免只给模型一个断章取义句子。
- 所有参数写入 `index_profile_version`；参数变化必须建立新索引版本，不能静默混用旧向量。

### 5.3 混合召回与重排

默认候选链路：

```text
BM25/关键词 Top 20 + Dense Vector Top 20
  -> RRF 融合
  -> 文档与父块去重
  -> 可选 Cross-Encoder / Provider Reranker
  -> Top 5-8 证据包
```

- 候选数量是初始预算，不是固定业务常量；小资料库自动缩小。
- RRF 作为默认融合算法，避免不同检索器分数尺度不可比。
- Reranker 不可用、模型未安装或超时时，保留 RRF 结果并明确降级，不撤回整个问答。
- 精确搜索零命中只代表字面没有命中，不能直接判定“资料中不存在”。
- Evidence Gate 检查来源数量、覆盖对象和最低证据要求；不满足时返回补充材料或缩小问题建议。

### 5.4 当前策略与升级门槛

当前实现不是“缺少一套完整 RAG”，而是有意停在已验证、可解释的第一条客户链路：本地 `BAAI/bge-small-zh-v1.5` FastEmbed（512 维）写入 Chroma；SQLite FTS5 的中文影子词项/BM25 负责字面、编号和专名；两路各取最多 20 个候选，经 RRF（`k=60`）、父块去重后输出最多 8 条检索证据。K3 再只向回答模型提供最多 4 个已核验父块，每个最多约 6,000 字符。当前 K0 固定资料集已扩至 7 份资料、11 个问题，包含 Markdown、跨父块长 Markdown、可提取文本 PDF 与 DOCX；关键词路径的必过召回为 `8/8`，页码/段落来源锚点为 `2/2`，平均 Recall@5/MRR 为 `0.850/0.850`，一次隔离运行的中位/P95 约 `13/18ms`。在已确认、本地只读复用的模型缓存下，真实 Hybrid 为 `8/8`、`2/2`、`1.000/0.950`、无答案 `1/1`，一次隔离运行的中位/P95 约 `308/403ms`；不同机器、缓存冷热和并发会改变延迟，不能把该小集结果写成生产 SLA。跨文档冲突题因此召回两份预期资料，但这只证明候选覆盖，不等同于已完成多跳推理或深度报告。Dense 使用单位向量的 Chroma L2 距离门槛 `<= 0.95`，防止无答案题被“最近邻”伪证据污染；该值来自本固定集，后续只能通过扩大标注集比较 Recall 和拒答率后调整。它只足以证明当前默认链路可用，不足以宣称参数已经全局最优。

以下决策对后续开发具有约束力：

| 能力 | 当前决定 | 进入实现的触发条件 |
| --- | --- | --- |
| 短文本全局信息补强、动态邻接扩充 | 已由父块、标题路径和有限邻接上下文部分覆盖；不再额外重复拼全文 | 固定评测发现短问句持续命中局部片段却缺主题判断时，先做可版本化的轻量上下文标注实验 |
| 查询意图与处理 | C4 目前只做显式资料库绑定与 K3 可信问答；不把普通聊天自动改写或猜测为知识库检索 | 扩充评测后先实现确定性 `RetrievalRouter`：非资料对话不检索，编号/专名优先关键词，概念问答走 Hybrid，比较和全局任务分别受限拆分或转 K4；出现稳定歧义样本后才增加一次轻量分类或查询改写 |
| 查询改写、子查询、HyDE | 保持关闭 | 首轮证据不足且用户问题含明确指代/多对象时，可比较“最多一次改写或最多三条子查询”；HyDE 仅离线实验，不能把假设文本直接当事实 |
| Cross-Encoder / LLM 重排 | 保持关闭；RRF 是默认精排前的最终排序 | 扩充后的固定评测证明 RRF 的前 5 结果持续错排，且 Cross-Encoder 在 Recall/MRR、延迟、包体和许可证上整体胜出时，才经 `RerankGateway` 接入。LLM 重排因成本、出站和不稳定性不作桌面默认 |
| 多向量表示 | 保持单一子块向量 | 资料类型出现标题、正文、表格、图片说明等明显异构且单向量评测失败时，再比较标题/正文等有限多向量；不为普通文本重复嵌入 |
| 语义分块 | 当前结构化标题/段落优先，字符滑窗兜底；父块约 6,000、子块目标约 1,200 字符、最小 320、重叠 160，参数由 `index_profile_version` 固化 | 在按 PDF、DOCX、Markdown 分类的真实评测集上比较命中率、断章率、索引耗时和磁盘占用后才调整；不根据单份演示文档改全局 chunk size |
| 上下文压缩 | 回答前的证据预算与来源锚点已是受控压缩；不使用会丢来源的摘要压缩 | 只有模型上下文或延迟成为实测瓶颈时，才引入保留 source_id 的 extractive compression，并加入引用闭合回归 |
| PDF OCR | 保持不做 | 用户批准扫描件场景、完成语言包/体积/隐私评估，并有 OCR 失败、页码映射和人工提示验收后，作为解析格式扩展单独立项 |

因此，近期优先级是扩大有代表性的评测资料、为 K3 增加确定性查询处理，再决定 K4 深度任务的最小范围；而不是把上述候选技术提前做成默认流水线。任何替换现有检索器、分块器或重排器的提交，必须同时更新离线评测、性能记录和版本化索引迁移策略。

## 6. 技术分层与依赖选择

### 6.1 稳定边界

- SQLite 继续作为知识库、文档版本、索引任务、引用、任务和审计的唯一产品事实源。
- 关键词和向量索引都是可重建的派生数据，不能成为唯一事实源。
- `VectorIndexAdapter` 隔离向量引擎，`EmbeddingGateway` 隔离本地/云端 Embedding，`RerankGateway` 隔离重排实现。
- `KnowledgeAgent`、Commander 和文档助手只能调用稳定服务协议，不依赖 Chroma/Qdrant/LangChain 内部对象。

### 6.2 K0 候选

- 稀疏检索：优先验证 SQLite FTS5 的 BM25 能力与中文分词影子字段；若中文质量不足，再比较独立 BM25 库，不能只因教材示例直接新增重依赖。
- 向量引擎：K0 已实测 `Qdrant Local` 与 `Chroma PersistentClient`。在本机 10k/100k 合成 512 维向量下，Chroma 的持久化与过滤查询表现明显更适合作为桌面默认，故 K1 首选 Chroma；Qdrant Local 保留为 Adapter 候选，未来若采用独立服务端部署须重新评估。完整数据见 `docs/KNOWLEDGE_BASE_K0_ADR.md`。
- Embedding：默认采用本地模型候选，紧凑中文模型与 BGE-M3/Qwen Embedding 等高质量模型包分级评估；大型模型包不强行塞入主安装包。云端 Embedding 只在用户明确允许资料出站时启用。
- Reranker：本地轻量 Cross-Encoder 与云端 Provider 都通过 Adapter 使用；MVP 必须支持关闭与安全降级。

具体模型、版本和许可证在 K0 通过官方资料、Windows wheel、模型卡和本机基准后记录，本文不提前承诺未经验证的依赖组合。

### 6.3 LangChain、LangGraph 与 DeepSeek Harness

- LangChain 只复用成熟 Loader、Splitter、Document、Retriever 或相关适配接口；AgentFlow 的 Pydantic 协议、权限、任务和引用仍由本项目拥有。
- 普通检索问答使用现有 Native Runtime，不为了使用框架建立多余 Graph。
- LangGraph 优先用于 Map-Reduce、并行分支、checkpoint 和可恢复深度任务，并通过适配层接入现有 Runtime。
- DeepSeek Harness 不参与普通文档索引和问答。只有深度任务证明 Native Runtime 无法满足恢复或工具编排需求时，才按 H2/H3 门槛进行隔离试点。

## 7. 长窗口与缓存

原生长窗口是受控的第三条执行路线，不替代检索：

- 单份明确选择的文档在 Provider 上下文预算内，并且全篇关系对任务确有价值时，才允许直接长窗口推理。
- 大型材料优先 Hybrid Retrieval 或 Map-Reduce；召回仍有歧义时再扩大上下文。
- 注入文本必须保留结构和来源，不能只拼接无标识正文。
- Provider 原生 Context Caching 通过能力 profile 按需启用；只有响应实际返回缓存 token 时才显示命中情况，不承诺固定命中率或降本比例。

本地缓存始终优先：

- 解析缓存：`content_hash + parser_version`。
- 分块缓存：`content_hash + splitter_profile_version`。
- Embedding 缓存：`chunk_hash + embedding_profile_version`。
- 检索短缓存：`knowledge_base_version + normalized_query + retrieval_profile_version`。
- Map 结果缓存：`parent_chunk_hash + task_contract_version + model_profile`。

更新、删除、解析器/分片/模型版本变化必须使相应缓存失效。缓存命中和失效都要可诊断，不能返回旧版本来源。

## 8. 数据模型草案

K0 只确认契约，不直接把半成品表写入生产数据库。K0.3 已将 Pydantic 契约、迁移顺序、generation 原子切换和删除失效规则写入 `docs/KNOWLEDGE_BASE_K0_CONTRACT.md`；K1 才按该设计建立正式表。至少需要表达：

- `knowledge_bases`：名称、描述、状态、默认检索 profile 和更新时间。
- `knowledge_documents`：活动版本、文件类型、受控引用、状态和内容哈希。
- `knowledge_document_versions`：解析器版本、索引 profile、来源范围和错误。
- `knowledge_parent_chunks` / `knowledge_child_chunks`：结构路径、原文、锚点、父子和邻接关系。
- `knowledge_index_jobs`：阶段、进度事实、失败项、取消和重试。
- `knowledge_queries`：问题、范围、路由、检索 profile、耗时和脱敏诊断。
- `knowledge_citations`：回答/报告中的结论与活动文档版本、块和原文位置关系。

向量值不存入普通任务 JSON 或日志；任务历史只保存向量 profile、命中 ID、排名、耗时和来源摘要。

## 9. 权限与隐私

- 导入只接受 Qt 明确选择并复制到受控知识库目录的文件，不接受客户端任意绝对路径。
- 本地解析、本地关键词索引和本地向量索引默认不联网。
- 云端 Embedding、Rerank 或回答模型会发送资料片段时，必须显示 Provider、数据类型和作用范围，并遵守现有权限模式。
- 检索内容始终标记为不可信数据；模型必须忽略资料中试图改变系统指令、权限或工具参数的内容。
- 模型不可见 API Key、数据库连接、绝对路径、权限决策、向量对象和未授权知识库。
- 删除知识库必须清理受控副本、活动/历史索引、缓存和可恢复元数据；保留的审计不得含原文。
- 知识库与长期记忆分离。资料不会因为被问答而自动写成用户偏好或项目约束。

## 10. Qt 信息架构

复用现有“知识库”导航，不增加新的一级导航。稳定布局优先在 `mainwindow.ui` 或独立 `.ui` 子窗口中维护。

1. **资料库**：列表展示名称、文档数、索引状态、更新时间和异常；主操作为“新建/导入”，更新、删除和高级设置放入行菜单或 Inspector。
2. **问知识库**：资料范围选择保持紧凑；回答拥有主要可伸缩阅读空间；来源位于可折叠侧栏，可查看片段并跳转文件位置。
3. **深度任务**：创建比较、摘要或审查任务，展示真实阶段、覆盖范围、暂停/取消和结果报告。

客户默认不需要理解 Embedding、chunk、Top K 或 RRF。高级诊断可展示“关键词/语义命中、重排前后、耗时和证据不足原因”，但不挤压主任务。运行阶段使用“解析、索引、检索、核对来源、生成回答”等真实状态，不伪造百分比。空闲、部分失败、无证据、模型失败和索引过期都必须有明确下一步。

## 11. 输出与失败处理

可信问答输出至少包含：

- `answer_markdown`：用户可读答案。
- `claims[]`：关键结论及其 `source_ids`。
- `sources[]`：文件、版本、章节/页码/段落/行号和短片段。
- `evidence_state`：`sufficient`、`partial` 或 `insufficient`。
- `retrieval_summary`：范围、路由、降级和耗时摘要。
- `warnings`：索引过期、资料冲突、来源不足或 Provider 问题。

失败与降级规则：

- 单个文档解析失败不阻塞其它已就绪文档，但任务必须显示未覆盖范围。
- 向量检索失败可降级关键词检索；关键词检索失败可降级受控逐文档搜索，不能伪造完整 Hybrid 成功。
- Reranker 失败保留融合结果；回答模型失败保留检索证据并允许重试。
- 引用校验失败时不交付对应结论，可返回证据列表供客户自行阅读。
- 同类失败有限重试，不能靠增加轮次掩盖分片、协议或 Provider 问题。
- 深度任务部分分片失败时允许“部分完成”，并列出未覆盖章节；不能把部分结果写成全库结论。

## 12. 评估体系

K0 建立固定、可版本化测试集，覆盖：

- 精确编号、专有名词和原文短语。
- 同义表达、错别字和口语化问题。
- 跨文档比较、多跳问题和冲突资料。
- 明确无答案的问题和提示词注入材料。
- 长文档章节召回、父子上下文完整性。
- 文档新增、更新、删除、索引切换和重启恢复。

检索指标：`Recall@K`、`MRR`、`nDCG`、Context Precision、Context Recall、重复率和来源覆盖率。

生成指标：Faithfulness、回答相关性、引用准确率、引用覆盖率、无答案判断准确率和冲突披露率。

工程指标：索引耗时、增量更新耗时、冷/热检索延迟、回答首阶段时间、token/费用、缓存命中和失败恢复率。

RAGAS 可作为离线辅助评估，不接入生产热路径，也不依赖 LangSmith。LLM Judge 结果只能辅助比较版本；引用身份、删除失效、权限、路径和索引原子切换必须使用确定性测试。阈值先通过基线数据确定，不复制教程中的通用目标冒充产品验收。

- 已完成 `POST /api/knowledge/answer/start` 的 `202 -> 真实阶段事件 -> 终态补读` 任务协议：检索、Evidence Gate、模型与 Verifier 的阶段事件及受限 Tool 摘要写入统一工作流历史；事件是可观察的语义阶段，不伪造 token 级流式正文。

### K4：深度任务

- **K4.1 范围快照已完成**：`KnowledgeDeepTaskScope` 会冻结当前活动 generation 的每个父章节、来源锚点、标题路径与字符范围；它不保存正文、路径或向量。资料更新后，旧 scope 在恢复前会被明确判为 stale，不能把旧 checkpoint 接到新 generation。`verify_knowledge_deep_task_scope.py` 已覆盖完整活动范围、无正文快照与更新后拒绝恢复。
- **K4.2 有限 Map checkpoint 已完成**：单次执行最多处理 24 个已冻结章节；每回合只读取并发送一个受控父章节给模型，结果只能引用当前 `map_unit_id`，随后立即写入 SQLite 检查点。模型失败会停止后续章节；客户显式恢复时仅重试失败节点，已完成节点不会再次调用模型。活动 generation 变化会在读取前或写入前停驻。`verify_knowledge_deep_task_map.py` 已覆盖章节上下文隔离、无正文任务快照、失败后恢复、完成后的幂等读取和更新后拒绝旧范围。
- **K4.3 两级 Reduce checkpoint 已完成**：每批最多合并 6 个已完成 Map 小结，最多 4 批再做最终合并；模型只读取受控 Map/批次 checkpoint，不重新读取原文。模型只提交概述、发现文本、待确认项与提示，Runtime 再将冻结批次投影为正式的来源范围、稳定编号与最终覆盖；模型不能自行扩展或伪造来源，也不会因复制动态 ID 失败。批次或最终合并失败会停驻并在显式恢复后只重试失败节点。当前实现按顺序运行，以先验证预算、恢复和来源闭合；并行化必须先增加共享预算预留与回归。
- **K4.4 可恢复后台 API 已完成**：`POST /api/knowledge/deep-tasks/start` 先冻结并保存无正文 scope，再以 `202 -> 真实阶段事件 -> 结果补读` 后台执行 Map/Reduce；`GET /api/knowledge/deep-tasks/{task_id}/result` 可从 SQLite 恢复范围与最终 Reduce checkpoint。同一任务在启动时固定一次 Model Runtime，Map/Reduce 不会因中途改配置而换 Provider。后台协程外的未知异常会收束为 SQLite `failed` 终态并保留检查点，避免历史遗留永久运行任务。当前没有 Qt 入口，且接口不创建文件或正式报告。
- **K4.5 协作控制已完成**：`POST /api/knowledge/deep-tasks/{task_id}/pause|resume|cancel` 复用 SQLite 控制信号并保持同一 `task_id`、scope 与已完成 checkpoint。暂停/取消在模型回合中只登记请求，在回合安全返回且结果落盘后才生效；继续不会重跑完成节点。暂停/取消不创建报告、不改变资料或强杀 Provider 请求。
- **K4.6 部分结果与导出资格已完成**：结果补读会基于 SQLite checkpoint 确定性给出 Map/Reduce 覆盖、已完成章节的小结和缺口；它不重新读取父块正文或调用模型。任务只有在全部 Map、全部预期 Reduce 和有效最终结果均完成时才进入 `ready_for_export`；失败、取消或待处理章节存在时只能提供部分预览，不能导出正式报告。损坏的历史最终 checkpoint 会被安全降级并显示脱敏警告。
- **K4.7 确认后的 Markdown 正式报告已完成**：`POST /api/knowledge/deep-tasks/{task_id}/report` 只接受客户确认的 `ready_for_export` 任务，确定性渲染冻结 scope、最终 Reduce、冲突与来源范围为 UTF-8 Markdown。文件以不覆盖方式写入 `output/knowledge_reports`，回读后才登记 artifact；任务历史通过统一受控预览/打开边界访问它，不暴露绝对路径。导出不重跑模型、检索或正文读取。
- **K4.8 Qt 客户工作台已完成**：资料库页只增加“深度分析”入口，完整 `ready` 索引才能发起任务。独立窗口提供任务类型与目标、真实事件阶段、冻结范围检查器、完整 Reduce 或部分 Map checkpoint 阅读、暂停/继续/取消、任务历史跳转和 `can_export` 约束下的确认导出；运行中也会低频补读范围和覆盖，但不会展示父块正文、路径、模型上下文或伪造百分比。Qt 只保留稳定 ID 和受控 JSON。
- **K4.9 大型资料目标聚焦已完成（历史行为）**：这一版本曾以 24 章为预算上限并冻结 `goal_focused` 范围。K4.15 已将它替换为完整范围的分层归并；旧 checkpoint 仍可读取、恢复和导出，但新任务不再创建目标聚焦范围。
- **K4.15 完整深度总结与资料对照表已完成**：全库深度总结会冻结当前活动索引中的全部章节，不再把 24 章当作客户可见上限。每个章节仍独立 Map 和落盘 checkpoint；Reduce 采用每节点最多 6 个输入的递归树，因而最终模型回合不会随着资料库变大而无界膨胀。供应商限流队列、一次瞬态失败重试、暂停/继续/取消与 generation stale 拒绝继续生效。客户侧只保留“全库深度总结”和“资料对照表”：对照必须显式选择 2 至 12 份资料，冻结其顺序，并在 UI 与 Markdown 报告交付真实行列对照表；模型遗漏表格时只能从已完成 Map 小结生成明确标注的保底行，不能退化为普通摘要。通用“风险与一致性审查”降为 Runtime 内部质量检查，新界面不再新建该类任务，历史审查任务仍可阅读和导出。
- 后续先完成 Qt 可见窗口验收，再讨论 Commander 深度任务准入；当前客户端工作台不等于已开放总指挥深度委派。
- 评估 LangGraph Adapter；Native Runtime 能满足时不强制迁移。

验收：覆盖范围、失败分片和引用完整可复盘；恢复不重复已完成 Map 节点。

### K5：长窗口与缓存优化

- **K5.1 本地检索短缓存已完成**：Retrieval Service 已为同一资料库、活动 generation、检索 profile、`top_k` 和规范化问题摘要哈希建立进程内 LRU 短缓存。缓存只复用受控证据包，不缓存模型回答、不写入 SQLite 或任务历史；generation 切换自动换键，临时 FTS/Dense 降级不缓存。结果与 Tool 审计仅展示实际 `hit/miss` 和命中年龄，不展示问题摘要哈希、TTL、缓存键或正文。专项回归覆盖命中、调用方副本隔离、`top_k` 隔离和 generation 更新后旧来源不复用。
- **K5.2 Provider Context Caching 能力映射与 usage 归一化已完成**：`ModelGateway` 对 DeepSeek、OpenAI、Anthropic 和自定义兼容入口分别声明“自动且可观测 / 显式请求 / 响应提供时可观测 / 未知”的协议边界，并把单次响应的输入、输出、总 token、cache read、cache creation 与 DeepSeek cache miss 归一为无正文计量。DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 只在响应实际出现时记录；Anthropic 仍需要请求内容显式携带 `cache_control`，当前 Gateway 尚未发送该标记；OpenAI-compatible 网关只有实际返回 `cached_tokens` 才显示观测。没有 `usage` 的响应保持 `not_reported`，不能被解释为缓存未命中或关闭。
- **K5.3 K4 深度任务 Provider 指标聚合已完成**：每个真实 `ModelRuntime` 的 Map/Reduce 模型回合会把无正文 usage 聚合写入同一 `WorkflowRun.metrics`；一次瞬态失败后的受控重试也计入真实请求数。指标同时保留“已发起请求数 / 返回 usage 的请求数 / 返回缓存字段的请求数”，并将 token 字段保持为可选值，避免 Provider 漏字段时被显示成零消耗。离线 mock、Tool 和资料正文不进入 Provider 指标；不写 API Key、prompt、模型正文、缓存键、账单价格或跨任务画像。
- **K5.4 索引性能可观测与解析复用核验已完成**：`KnowledgeIndexJobRecord` 持久化无正文的解析/分块、向量构建、关键词 generation、总耗时和已复用解析版本数。`ready/parsed` 版本会直接复用已持久化的解析与父子块；当前仍按 generation 重建 FTS，且本地向量启用时仍重新嵌入该 generation 的子块。不能复制旧 Chroma 目录来伪造复用，后续是否按内容哈希复用 embedding 必须以这些指标和 generation 隔离回归为前提。
- **K5.5 无变化索引快路径已完成**：客户再次请求索引时，只有资料库完整 `ready`、当前候选版本清单与活动 generation 完全一致、Profile JSON 未变，且没有等待补建的本地向量时，才返回原已完成 job 并登记脱敏复用审计。资料更新、Profile 变化、部分失败、向量失败，或客户已准备本地 embedding 模型但旧 generation 仍为 `pending` 时，必须创建新 generation 完整构建，不能以快路径掩盖能力变化。
- **K5.6 增量向量复用已完成**：候选 generation 只从当前活动且 `ready` 的向量 generation 受限回读；同一资料库、完全相同的 Index/Embedding Profile、相同 `child_chunk_id` 与相同 `content_sha256` 缺一不可。满足条件的未变子块读取旧向量后写入新的独立 generation，新增或更新子块才调用本地 Embedding。旧 collection 缺失、损坏或部分向量不可读时逐块安全回退为新嵌入，不复制 Chroma 目录、不向 SQLite 写入向量，也不让错误向量跨 Profile、跨资料库或跨 generation 流动。`KnowledgeIndexJobRecord` 只记录本代写入、复用与新嵌入的子块数量，不能据此推断具体内容或成本节省。
- K5.3-K5.6 当前只覆盖 K4 的长任务 usage、索引阶段性能、无变化快路径和受限向量复用，不把它们伪装为长期记忆、SQLite 计费账单、用户可见命中率、全局向量缓存或已节省成本。后续再按真实收益推进受控 Map 缓存、其它任务指标、设备性能分级和可选模型包。
- 根据真实指标优化 TTFT、并发、磁盘和内存占用。

验收：缓存版本正确、更新后不返回旧来源；界面只展示实际可观测的缓存数据。K5.1 不把本地短缓存表述为 Provider Context Cache 命中、模型成本下降或跨进程持久记忆；K5.2 不将静态 Provider 能力表述为某次请求已经命中；K5.3 不将部分 Provider usage 合计表述为完整账单或命中率；K5.4 不将阶段耗时或解析复用数表述为向量缓存命中或成本节省；K5.5 不将无变化快路径表述为资料更新后仍跳过重建；K5.6 不将相同 ID/哈希的受限旧向量读取表述为跨资料库/跨 Profile 缓存、内容更新后复用、Chroma 目录复制或已验证的成本节省。

#### K5 后续路线与放行条件

K5.1-K5.6 只是当前一轮的检索、用量和索引性能闭环，不是知识库产品的终点。后续按下列顺序推进：

1. **K5.7 长上下文路由与成本边界（已完成）**：K3 固定选择有限检索证据，K4 固定选择单章 Map/分层 Reduce。每次真实模型调用在请求前记录无正文的实际输入字符数、内部字符预算、路由和 Provider 长窗口状态；超预算直接停驻，不会因模型窗口更大而改为整库正文直灌。DeepSeek V4 Flash/Pro 的 1M 窗口只记录为“已确认但未启用”；未知/自定义模型保持未确认。Provider usage/cache 仍只以真实响应为准，长上下文缓存不作为正确性前提。
2. **K5.8 设备性能分级与运行队列（已完成）**：`GET /api/knowledge/performance` 只聚合已保存的 completed 索引总耗时、当前进程无正文的检索/深度执行耗时、逻辑核数和数据目录所在卷的可用空间，给出低/中/高资源建议、慢阶段提示和磁盘提示。索引与深度任务分别 FIFO 串行；低配设备只允许一个重任务通道，中高配最多允许一条索引与一条深度链并行，以控制 CPU、内存、SQLite 写入和 Windows 文件句柄，普通检索/问答不排队。任务、队列和性能观察不保存客户正文、问题、文件名、路径、向量或设备身份；进程重启后队列与短时观察自然清空，业务 checkpoint 仍以 SQLite 为准。
3. **K6.1 质量评测基线（已完成）**：`scripts/fixtures/knowledge_k6/retrieval_quality_cases.json` 提供 8 道版本化、可审查的合成题，其中 5 道 `required` 守住编号、关键词、来源锚点、长材料后段和拒答，3 道 `diagnostic` 覆盖语义改写、跨资料处置与不可信材料。`verify_knowledge_retrieval_baseline.py --k6-quality` 在真实受控导入、分块、generation、FTS 与证据回读上输出仅含夹具 ID/分组聚合/耗时的 JSON 指标，不调用 LLM、不下载模型，也不收集客户问题或正文。当前关键词基线为 required `5/5`，语义改写夹具仍出现一个 `no_result` 缺口；该证据只说明值得评估候选策略，不能宣称某种策略已经启用。
4. **K6.2 本地 Hybrid 候选验收（已完成）**：同一 K6 题集下，本地 Hybrid 保持 required `5/5`，并将语义改写从关键词路径的 Recall/MRR `0/0` 提升至 `1.0/1.0`；`--require-k6-diagnostic-pass` 已把已标注失败模式纳入候选验收。代价是本机中位检索约从 `7ms` 上升到 `172ms`，P95 约从 `16ms` 上升到 `396ms`。因此现有“索引已准备时走 Hybrid、不可用时可解释降级到关键词”的产品路线足够覆盖当前评测，不新增受限子查询、metadata 过滤、Cross-Encoder 或 LLM Rerank。以后只有新的脱敏失败夹具持续证明不足，才按同一规则逐项重启实验。
5. **K7 扫描件与图片型 PDF OCR（已确认，K7.1 技术试验下一步）**：用户已选择只读、本地优先的 OCR 增强，详见 `docs/K7_OCR_PRODUCT_PLAN.md`。它将扫描 PDF 与 PNG/JPG/JPEG 纳入现有文档/资料库解析，并保留页码来源；模型准备必须由客户显式确认，未准备不自动联网。K7.1 先在隔离环境验证本地 `OcrAdapter` 的 Windows 依赖、性能、来源锚点、失败恢复和打包边界；复杂表格、公式、手写体、云端视觉、网页/云盘/数据库连接器、外部知识源、多人 ACL、行业包和知识图谱均不进入 K7 MVP。

## 14. 与现有模块的关系

- Commander：C4 已可按 action 准入委派一个客户显式选择的知识库可信问答；深度任务待 K4 单独准入。
- 文档助手：通过 Retrieval Service 读取知识库证据制作文档/PPT，不复制索引。
- 数据工作台：首版不把原始表格自动入库；只允许未来经确认的分析摘要或正式产物入库。
- 长期记忆：继续保存客户确认的短事实，不与知识库文档或向量索引合并。
- Verifier/Evaluator：继续作为共用验证层，负责引用、索引状态、覆盖和报告契约，不新增独立页面。
- DeepSeek Harness：仅为经批准的深度任务提供可选 ExecutionBackend，不接管知识库、权限和审计。
