## 1. 如何判定任务完成

一次交付要分别回答：工具是否正确执行、结果是否满足用户要求、用户能否预览修改并拿到成品、失败后能否恢复。API 200、模型自评“很好”、文件存在、数据库登记成功，均不足以单独证明任务完成。

| 层级 | 评测对象 | 是否可用 Mock | 证明什么 |
| --- | --- | --- | --- |
| E0 契约与边界 | 规划 schema、版本、权限、错误与状态、次数上限 | 可以，禁止真实联网 | 边界和异常路径正确 |
| E1 确定性媒体工具 | 真图像、真音视频、保存再打开、文件解码与时间轴 | Provider 可替身，文件处理必须真实 | 工具实际加工结果符合数学/格式约束 |
| E2 模型与内容质量 | 真实修图、ASR、语义选段、翻译与配音 | 不可以 | 在固定材料和预算内，内容达到可用水平 |
| E3 客户端与交付 | Qt 与调度台完整流程、取消恢复、编辑后导出 | 离线异常可用替身；发布证据必须含真实主路径 | 用户能完成任务、看到准确状态并取回实际产物 |

E0/E1 通过不代替 E2/E3。某一 Provider 通过不代替其他模型和运行配置通过。首版 Windows 图片验证不代替视频验证或其他操作系统验证。

评测服务于产品闭环，不服务于“把所有候选技术都测一遍”。内部开发门槛只证明当前选定路线值得接入；独立盲评、完整素材集、DPI 和人工流程集中在质量/发布门槛执行。未进入当前执行路径的 Matting、Segmentation、VLM 或其它候选模型标记为 optional，不得阻塞主线，也不能因有探针结果就写成正式能力。

## 2. 固定素材、任务与拆分

### 2.1 建立版本化评测集

先从自有或明确授权的真实照片、口播、生活/演示视频取得素材。合成素材只承担可精确测量的几何、同步、损坏和异常测试，不用于声称真实修图审美或识别准确率。

| 评测集 | 最小规模与拆分 | 必须覆盖 |
| --- | --- | --- |
| IMAGE | 12 张真实图片，每图 3 个任务，共 36 个；8 图/24 任务开发集，4 图/12 任务留出集 | 人像、杂乱背景、透明边缘、文字/标志、低照度、细小目标；含单次与连续修改 |
| VIDEO | 8 段授权视频，每段 2 个剪辑任务，共 16 个；5 段/10 任务开发集，3 段/6 任务留出集；总时长至少 30 分钟 | 口播重录、多人轮流讲话、停顿、片段顺序、横竖视频；记录源标注的可接受剪辑边界 |
| LOCALIZE | 6 段中英音视频，每段至少 20 个有效字幕段，共至少 120 段；4 段开发集，2 段留出集且分别覆盖中译英/英译中 | 数字/单位、人名、专业术语、否定句、长短句与语速变化 |
| INTENT | 至少 60 条自然口语指令，每类至少 10 条 | 单步、多步、连续指代、缺少输入、越界请求、只询问历史/能力；正例与负例分别统计 |
| MEDIA-EDGE | 至少 12 个小型确定性夹具 | EXIF 旋转、alpha、蒙版变换、VFR、无音轨、双音轨、损坏文件、伪扩展名、空音频、Unicode 路径、源音画偏移、同步闪光/脉冲 |

拆分按源素材完成，同一视频的相邻裁片、同一照片的压缩版或变体不能跨开发/留出集。留出集在参数冻结后一次完整运行；为调试看过的留出失败项移入开发集，并补充独立留出素材，保留历史结果，不能覆盖失败记录。

MM-0 只建立足以判断模型路线可行的代表样本和 INTENT 小集；完整 IMAGE 开发集/留出集在 MM-2 的 G2 前冻结。MM-4 再补 VIDEO 和对应边界材料，MM-6 补 LOCALIZE。后续集合未建立时不得将对应发布门槛标为通过，但不阻塞更早阶段的内部契约开发。

### 2.1.1 模型 Profile 选型探针

模型 Provider 返回 HTTP 200、能生成一张图片或能输出一段文本都不构成发布准入。每个实际启用的 Profile 都要建立独立记录，包含模型/权重版本、Provider/端点、许可、输入输出限制、设备或实际费用、超时/重试策略和固定参数。`media_planning` 与 `media_image_edit` 是 MM-2 的 required；`media_matting`、`media_segmentation` 和 `media_vision` 只有进入实际方案时才转为 required；`media_transcription` 在 G4 前补齐，`media_translation`/`media_speech` 在 G6 前补齐。

| 探针编号 | Profile | 最低通过证据 | 失败时的结论 |
| --- | --- | --- | --- |
| MODEL-01 | `media_planning` | 20 条冻结图像意图中记录完整计划正确数、schema 失败、错误工具选择和修正次数；工具选择、目标对象、局部/全局范围均正确才算样本通过 | 调整提示/模型或淘汰候选；不得用人工改写后的计划充当模型成绩 |
| MODEL-02 | `media_image_edit` | 内部开发至少覆盖一次真实输入、输出回读、请求标识和三类代表任务；G2 再要求局部消除、换背景、中文文字编辑各至少 3 个固定样本和独立复核 | 缺少图片输入、结果图或失败状态时不进入 MM-2；质量未达标时不通过 G2 |
| MODEL-03 | `media_matting` / `media_segmentation` | 仅在方案启用时 required；人像发丝、商品边缘、透明/细小物体和复杂背景均有结果，并记录人工修正次数与峰值资源 | 质量或资源不适配则关闭自动能力，回退手工蒙版或不依赖该模型的路径，不阻塞无依赖主线 |
| MODEL-04 | 本地或云端图片路线 | 内部开发需覆盖拒绝、限流、超时未知结果、调用方取消和 usage 字段；G3 再核对费用、恢复、资源和用户可见状态 | 失败语义不准确或会盲目重复收费时阻断开发；费用资料未齐时阻断发布 |
| MODEL-05 | ASR、VLM、翻译、TTS | 在 G4/G6 按阶段增加时间戳、视觉输入、术语保留、可懂度和时长探针；每项绑定实际模型 ID | 不把另一模型、另一语言或演示页面的宣传迁移为本项目能力 |

### 2.1.6 MM-4 受控媒体源与工具协议基线

2026-09-24 已新增 `media_source_preparation`，将音视频原件与既有图片 revision 隔离。它只接收上层已读入的内存字节，使用 `source_id` 绑定项目范围、文件哈希和受控私有目录；`ffprobe`/`ffmpeg` 仅取得服务端由 ID 解析的路径，命令没有来自模型或客户端的 codec、filter、路径或 Shell 参数。提取固定为首条已探测音轨、`16 kHz` 单声道 PCM WAV，并在不超过 `7 MiB`、WAV 回读和 SHA-256 一致后登记为可交给 ASR 的派生音频。

`verify_media_source_preparation.py` 使用临时目录与工具替身覆盖范围拒绝、源篡改拒绝、ffprobe 容器/音视频流解析、固定 `-map 0:<stream>`/`-vn`/`-ac 1`/`-ar 16000`/`pcm_s16le` 命令、派生 WAV 回读和同输入复用；不运行真实系统工具、不会读取用户媒体或调用模型。

2026-09-24 已以 `probe_media_source_preparation.py --execute` 运行一次真实 E1：夹具为程序生成的 `2 s` 黑色视频与 `880 Hz` 音调，使用显式传入的 `Gyan.FFmpeg.Essentials 9.0.1` 可执行文件。真实 `ffprobe` 识别出 `320x240/25 fps` MPEG-4 视频和第 `1` 条 `48 kHz` 单声道 AAC 音轨；真实 `ffmpeg` 经固定命令提取出 `16 kHz` 单声道 PCM WAV，回读为 `32,000` frames、`64,078` bytes、`2.000 s`，派生文件 SHA-256 与登记值一致。证据位于忽略目录 `data/media_evaluations/media_source_preparation_e1_20260924T065700Z/`，只含生成夹具、受控副本和不含绝对路径的 manifest；模型/Provider 请求数为 `0`。应用服务尚未配置 `AGENTFLOW_FFMPEG_PATH` / `AGENTFLOW_FFPROBE_PATH`，故 `/health` 仍会诚实显示未就绪。

E1 只证明本地编解码命令与受控文件协议可以闭环，仍不构成 `MODEL-05`、转写任务、字幕交付或 `G4` 通过。

2026-09-18 从 BiRefNet 官方 GitHub Release `v1` 获取 `BiRefNet-general-bb_swin_v1_tiny-epoch_232.onnx`。本机缓存文件为 `224,005,088` bytes，SHA-256 为 `5600024376F572A557870A5EB0AFB1E5961636BEF4E1E22132025467D0F03333`；权重位于忽略目录 `data/media_model_cache/`，不写入 Git，也不会被应用自动下载。运行依赖独立登记在 `backend/requirements-media-worker.txt`，主后端通过可选导入和就绪检查保持可启动。

当前机器只检测到 2GB 显存的 NVIDIA GeForce GT 730，因此没有把完整 BiRefNet 或 SAM 2.1 装入桌面端或主后端。Tiny ONNX 在 `CPUExecutionProvider` 下可加载固定 `1x3x1024x1024` 输入和 `1x1x1024x1024` 输出；程序生成 `960x640` 几何诊断图后得到同尺寸、可由 Pillow 回读的 `L` alpha PNG，实际推理 `13,377 ms`。证据目录为 `data/media_evaluations/birefnet_foreground_mask_20260918T025138Z/`。

随后使用 `prepare_media_evaluation_fixtures.py --execute` 从固定 Wikimedia Commons 文件页建立公开夹具集：CC0 发丝人像、CC BY-SA 4.0 商品场景和公共领域透明玻璃饮料图。每张保存文件来源页、许可证、作者/署名元数据和 SHA-256；`probe_birefnet_public_fixtures.py --execute` 在该集合上输出相同尺寸 alpha，耗时分别为 `13,053 / 11,157 / 11,303 ms`，证据为 `data/media_evaluations/birefnet_public_fixtures_20260918T030044Z/`。

人工复核发现：人像外轮廓可以作为粗前景建议；商品场景只覆盖显著碗/饮料，无法根据用户选择区分多个商品；玻璃和液体区域被近似为不透明，并出现孔洞。基于这一真实夹具筛选，`BiRefNet-general-bb_swin_v1_tiny` 不通过 `media_matting` 或 `media_segmentation` 的候选准入，不注册到模型列表。它仍可保留为离线研究参考，但不能在产品中描述为抠图或选区能力；该结论不阻塞不依赖自动抠图的 MM-2 主线。

为使真实失败测试接入前的行为可预测，`verify_qwen_image_edit_provider.py` 以 MockTransport 覆盖了明确拒绝 `400`、限流 `429`、服务端 `503`、提交超时、连接中断和调用方取消：明确 4xx 的结果状态为 `rejected`；429 提供受控等待提示；提交超时、连接中断和 5xx 的结果状态为 `unknown`，适配器禁止自动重发；取消必须原样抛回调用方。该离线契约防止后续 Runtime 把不确定结果当作“安全失败”，但不替代真实 Provider 的超时、取消和未知结果查询验收。

`probe_qwen_image_unknown_outcome.py --execute` 已执行一次真实云端超时探针：内存中生成 `512x512` PNG，固定 `qwen-image-3.0-pro`，客户端总等待阈值 `1.0 s`。调用约 `3,289.228 ms` 后得到 `QwenImageEditOutcomeUnknownError / request_timeout`；记录为 `outcome=unknown`、`safe_to_retry_automatically=false`，不下载结果 URL、不重发、不落盘输入图。证据目录为 `data/media_evaluations/qwen_image_unknown_outcome_20260920T030712Z/`。

完整 manifest 位于 `data/media_evaluations/local_media_worker_resilience_20260920T020649Z/`。两条测试均在监督完成后确认没有残留 Python 进程。该样本表明两种候选均必须单独运行并限制并发，尤其 Lite Matting 的 `2.64 GiB` RSS 不适合驻留 FastAPI 或 Qt。Lite 的第二次推理反而慢于第一次，不能宣传暖运行会加速。

这不是正式 worker 的协作取消成绩：父进程是在测试钩子处强制终止子进程，以确认尚未提交的内存结果不会变成半成品 artifact。推理执行期间的协作取消、任务 checkpoint、用户可见状态和并发队列仍属于 MM-3。它也不改变 Lite/SAM 的 `pending_human_review` 状态，不替代 SAM 负点/多轮修正与透明细节质量验收。

## 4. 确定性验收与阻断项

下列检查属于 required，适用阶段必须 100% 通过，任一失败阻止该能力准入。比例均同时报告原始通过数/总数。

| 检查编号 | 检查内容 | 判定方法 |
| --- | --- | --- |
| HARD-01 | 原件与项目范围 | 处理前后原件哈希一致；直接 API 访问其他 project 的素材、缩略图、任务、导出均被拒绝 |
| HARD-02 | 输入和命令边界 | 无效尺寸/时间/工具被拦截；文件签名与类型核对；路径逃逸、远程 URL、Shell 片段不能进入可执行参数 |
| HARD-03 | 版本与批准一致 | 批准绑定 plan/revision；批准后人工修改、并发提交和迟到结果不能覆盖新 revision |
| HARD-04 | 可逆历史 | 连续 10 次混合编辑后撤销/重做并重启，画布与历史结果一致；撤销不调用生成模型 |
| HARD-05 | 蒙版和局部保护 | 在无损 PNG、未要求全局变换的用例中，既定有效蒙版之外像素逐点相等；蒙版与源版本匹配 |
| HARD-06 | 真实文件交付 | 回读尺寸/通道/透明度、完整解码音视频、字幕语法和编码；假后缀、空文件、截断输出不能登记为成功 |
| HARD-07 | 交付合同 | 用户要求的必需产物逐项存在且通过对应检查；只有部分结果时显式列出缺口 |
| HARD-08 | 文件与登记崩溃窗口 | 分别在临时写入、原子提交、artifact 登记、终态事件前后注入崩溃；恢复后不丢已确认交付、不重复登记 |
| HARD-09 | 取消、恢复与未知结果 | 不重复提交已完成付费动作；无法确认远端结果时停驻并解释；取消后不派生新动作 |
| HARD-10 | 参数真实生效 | 任务指定的 Provider、模型与受支持参数进入实际请求；不支持的能力执行前拒绝，无静默换模型 |
| HARD-11 | 无隐式外发与下载 | 缺少出站/下载授权时零对应网络请求；未启用媒体功能时不加载或下载重模型 |
| HARD-12 | 上下文内容隔离 | 图片文字、字幕或转写里的指令作为素材处理；不能触发任意命令、额外外发或改变工具权限 |
| HARD-13 | 依赖失效 | 缺模型、解码器失败、磁盘不足、worker 崩溃均有准确错误和可恢复状态；现有聊天仍能工作 |
| HARD-14 | 提交与任务事件一致 | 双击/同 request_id 重试只创建一个逻辑任务；重连后事件有序去重；只有真实运行态显示活动状态；任务终态、界面与产物记录一致 |
| HARD-15 | 缓存与删除 | 改源、蒙版、参数、模型版本必须失效；有效缓存可复用；清理不删仍被工程/撤销引用的材料 |
| HARD-16 | 时间轴一致 | 半开区间、拼接、重排、原始音画偏移、VFR 与字幕映射正确；代理视频与源素材坐标一致 |
| HARD-17 | 限次与预算 | 原子预留预算；修正/重试计入调用与费用；超过冻结上限不发新请求，显示停止原因 |

HARD-05 中有效蒙版包含预先声明的羽化范围，必须在生成前固定；不得事后扩大蒙版掩盖越界。JPEG 导出另做压缩质量验证，不能用逐像素不等误判局部保护，也不能用 JPEG 差异豁免 PNG 中的越界修改。

## 5. 内容质量与量化目标

### 5.1 指标定义

- 一次任务由一个固定输入/初始工程和规定的用户指令序列组成。生成多张候选不能增加任务分母。
- 首次成功率：第一次结果满足该用例全部硬约束和内容评分的任务数 / 全部任务数；失败、超时和无输出都计入分母。
- 最终成功率：最多一次预算内修正后的通过比例；另行记录用户修改次数，不能与首次成功率混报。
- 规划正确率：目标对象、工具选择、关键参数、依赖和保留约束均正确的完整计划比例；不能只统计 JSON 可解析率。
- 留出集与开发集、单轮与多轮、各任务类型分别报告。小集合报告 x/n；不得将其泛化为生产成功率。
- 盲评采用两名人工评审，其中至少一人不是该功能实现者；隐藏模型名称与方案顺序，评分相差 2 分及以上时复核，分歧不自动算通过。模型自评仅供定位问题。

### 5.2 首批目标

下列目标在各集合首次正式评测前冻结。可根据前期技术试验提出带理由的版本修订，但必须保留原目标和原结果，不能以降低门槛把失败改成通过。

| 指标编号 | 对象 | 准入目标 | 备注 |
| --- | --- | --- | --- |
| QUAL-01 | 支持范围内的完整计划 | 正确率 >= 90%；越界/历史询问等阻断类正确率 100% | 正负例分开；同义措辞和多轮指代单列 |
| QUAL-02 | 图片最终内容质量 | 开发集与留出集分别 >= 90% 任务通过；12 个留出任务至少 11 个通过；各任务类别 >= 80% | 首次成功率也必须报告；所有 HARD 均须通过 |
| QUAL-03 | 图片人工评分 | 指令符合度、主体/非目标保护、边缘与自然度各 >= 4/5 才算该任务通过 | 5=可直接用，4=轻微瑕疵不影响用途，3=需明显返工，2=主要目标错误，1=不可用 |
| QUAL-04 | 视频语义选段 | 开发集与留出集分别 >= 90% 任务通过；用户明确要求保留的词句/片段零遗漏 | 6 个留出任务意味着需 6/6，通过数公开，不能舍入放宽 |
| QUAL-05 | 剪辑边界 | 自动边界落在人工可接受区间，或距最近允许边界 <= 200 ms；全部指定精确裁剪夹具在 1 个输出帧内 | 边界达标仍不能截断关键词；标注允许区间比固定唯一时间点更符合真实剪辑 |
| QUAL-06 | 音画同步 | 闪光/音频脉冲基准相对源文件的偏移变化绝对值 <= 80 ms；开始、中间、结尾均通过 | 不把 ffprobe 时长相近当作同步证据；真实素材追加人工听看 |
| QUAL-07 | 首批清晰语音转写 | 中文 CER <= 15%，英文 WER <= 20%；开发/留出分别计算并公开字符/词计数 | 使用冻结人工校对文本和规范化规则；噪声/重叠语音单列 diagnostic，不冒充已覆盖 |
| QUAL-08 | 翻译准确性 | 关键数字、单位、否定含义和必须保留名称零错误；术语表符合率 >= 95%；准确/自然/断句各 >= 4/5 的段落 >= 90% | 对整段视频再做连贯性检查；段落级大样本不能掩盖某一视频整体失败 |
| QUAL-09 | 字幕可读与对齐 | 时间合法且不无故重叠；每条最多 2 行；初始上限中文每行 20 字、英文每行 42 字符；目标阅读速度中英分别 <= 12 字/s、20 字符/s | 规则、标点计算和专名例外在 LOCALIZE 基线冻结；需要改写/分段时保留原文 |
| QUAL-10 | 配音质量 | 可懂度、自然度、语气适配各 >= 4/5 的段落 >= 90%；关键内容无遗漏、错译和音频截断 | 与语速/停顿共同复核；不以音频时长匹配代替听感 |
| QUAL-11 | 配音时间映射 | 各段不互相覆盖或裁掉词尾，误差 <= 200 ms；整段音轨不截断视频尾部 | 初始速度调整范围 0.9-1.1 倍；超范围应调整译文/分段或提示，不能无限加速 |

CER/WER 使用编辑距离定义，报告替换、删除、插入及参考长度。数字和专名检查在规范化前单独完成，防止把错误数字规范化掉。无语音夹具不计算 CER/WER，按“不生成虚构转写”单独判定。

### 5.3 基线与用户价值

| 对照 | 使用方式 | 防止错误结论 |
| --- | --- | --- |
| 直接模型调用 | 对适用图片任务，以相同源图、蒙版、模型和预算直接提示作为基线 | 若 Agent 只是增加步骤却不改善局部控制/多轮修改/交付，不算已证明价值 |
| 人工编辑 | 至少 6 个代表任务，使用明确记录版本的现有工具人工完成 | 同时统计 Agent 等待、人工纠正与检查时间；不同人/工具熟练度写入报告 |
| 冻结前一版本 | 同一夹具、模型 profile、硬件和配置 | 新方案不能靠更高分辨率限制、更多费用或更强模型掩盖架构退步 |

初始用户价值目标：在达到同等质量的代表任务中，“实际操作 + 必需修正”的中位时间比人工基线减少至少 20%。总墙钟耗时单独报告；如果质量达标但价值目标未达到，只能列为实验能力并继续优化，不能直接标正式准入。

## 6. 性能、费用与资源

| 档案 | 测量条件 | 必须记录 |
| --- | --- | --- |
| CPU | Windows、无 GPU 加速、明确线程数 | CPU 型号、RAM、解析/导出耗时、进程树峰值内存；不承诺本地大生成模型可运行 |
| GPU | 明确 GPU/显存、驱动与推理版本 | 首次加载、暖运行、显存峰值、OOM 行为、队列等待 |
| Remote | 明确 Provider/模型与输入输出参数 | 网络等待、上传字节、实际 usage、任务/图片/音频计费单位与估价版本 |

每个正式 profile 必须在 G2/G4/G6 冻结具体最大素材规模、任务超时、进程内存/显存/磁盘上限和费用上限；缺少这些值时不能判该 profile 对用户准入。内部开发真实调用也必须先设置请求次数和预算上限。本文输入规模是产品建议，不能替代机器实测；费用无计价依据时记录 unknown，不写成 0。

| 指标编号 | 目标与测量方法 |
| --- | --- |
| PERF-01 | 本地点击/取消的可见反馈 P95 <= 100 ms，至少 30 次交互；不把模型返回耗时算为首次反馈 |
| PERF-02 | 重任务运行时使用 Qt 事件循环探针与后台 health 请求检查响应；与同机空闲基线比较，记录 P95 与最长停顿，出现 >= 1 秒 UI 停顿即失败 |
| PERF-03 | 本地可终止 worker 在取消后 5 秒内退出并释放文件句柄；远端在途调用单独记录，取消后新调用数必须为 0 |
| PERF-04 | 未启用媒体模块时无重模型下载/加载；冷启动耗时增加不超过 max(基线的 15%, 300 ms)，空闲内存增加不超过 50 MB |
| PERF-05 | 默认重任务并发 1，队列/磁盘/内存不超过冻结 profile；错误或取消后没有属于本次任务的残留进程 |
| PERF-06 | 导出阶段失败后恢复，已验证生成/转写步骤重复调用数为 0；只统计仍有效且文件存在的缓存 |

冷启动至少 5 次；工具暖运行建议 30 次。真实模型不得为凑样本无预算重复调用：样本少于 30 时报告原始样本数、中位数、最大值，不把少量请求的 P95 当稳定性能承诺。首次模型下载、加载、排队、推理、渲染和用户审阅分别计时。

## 7. 故障注入与原有功能回归

| 编号 | 注入场景 | 预期行为 |
| --- | --- | --- |
| FAIL-01 | Provider 401/400/429/5xx、连接失败、结构不符 | 分类处理；无权限/参数错误不盲重试；限流尊重 Retry-After 与预算；不泄露 Key |
| FAIL-02 | Provider 接收请求后断线 | 保存请求标识并对账；不可确认结果时停驻，不能自动重复消费 |
| FAIL-03 | 生成已完成，导出前应用退出 | 恢复已验证生成结果，继续导出；源或版本改变则明确失效 |
| FAIL-04 | 新 revision 已提交，旧 worker 迟到 | 旧结果不能覆盖当前工程，可标记为旧版本候选 |
| FAIL-05 | 磁盘满、输出路径不可写、文件仍被播放器占用 | 无假成功；保留已完成结果，释放可释放句柄并提供重试入口 |
| FAIL-06 | GPU OOM、依赖缺失、worker 非零退出 | 有准确原因和能力状态；不静默外发到云端，不使主应用退出 |
| FAIL-07 | TTS 失败但字幕完成 | 保留字幕并列明缺少配音，后续只重做失败部分 |
| FAIL-08 | 任务取消后 WebSocket 断开又重连 | 保持 cancelled，去重历史事件；不能恢复为 running 或自动重试 |

## 8. 阶段门槛映射

### 8.0 门槛依赖修正（2026-09-23）

旧方案把候选模型独立盲评、历史费用补齐、完整图层/蒙版 GUI 和多档 DPI 都放在 AI 闭环开发之前，导致团队不断完善底座和评测，却迟迟没有把模型能力交到用户路径中。门槛现拆成“能否开始内部开发”和“能否正式发布”：

- `G0-DEV`：图片模型内部开发准入。只要求当前选定的规划/图片编辑路线可真实调用、输出可回读、失败不会盲目重发，并能记录 request ID/usage 字段。
- `L1-DEV`：最薄媒体底座开发准入。只要求受控导入、原件保护、新 revision、撤销、导出回读、Runtime/Artifact 和一条客户端冒烟成立。
- `G2-DEV`：AI 修图开发质量准入。要求固定真实输出全部可回读，并按任务类别验证最低效果；它给出可复现的开发结论，不承担审美或独立性背书。
- `G2`：AI 修图正式质量准入。要求 `G2-DEV` 保持通过，再补独立人工复核、局部保护、多轮版本与冲突处理；可选模型仅在实际启用时 required。
- `G3`：用户发布准入。要求费用、权限、取消恢复、完整 Qt 流程、DPI、可访问性和原功能回归。

`G0-DEV`/`L1-DEV`/`G2-DEV` 通过只允许继续开发，不改变 `runtime_ready` 和对外能力声明。历史无法追补的逐请求金额保持 unknown，不以重复付费重跑补材料。空白独立评审表属于 `not_run`，不得写成模型或功能失败。

### 10.1 MM-1 并行基础记录（2026-09-21）

以下是调整路线前已经完成的图片工作区工程记录。这些能力作为可复用底座保留，但不是继续扩建通用图片编辑器的依据：

- `backend/app/services/media_workspace.py` 与 `backend/app/database/media_workspace_repository.py`：项目内原件副本、不可覆盖的 PNG 修订版本、旋转/镜像/灰度和参数化调色/裁剪/缩放白名单操作、矩形透明蒙版、栅格图层叠加和导出文件原子写入与 Pillow 回读校验。蒙版是版本绑定的 `L` 模式 PNG，保存选区参数、父修订、文件哈希和尺寸；应用时与当前 Alpha 相乘，选区外透明而不会抹掉已有透明度。栅格图层固定来源素材/修订、位置与不透明度；manifest v7 在每个组合修订中保存底图和完整图层栈快照。勾选可见性或重排图层时，从冻结底图和冻结来源版本重渲染下一份 PNG，旧修订的像素与图层状态都保持不变。每个修订保存父版本、规范化参数、尺寸和 SHA-256；调色保留 alpha，裁剪检查当前图像边界，缩放限制目标像素总量。项目、素材、修订、蒙版、图层、导出和历史事件元数据作为一个校验过的 SQLite 快照保存，二进制文件始终在受控目录；旧 v1-v6 JSON manifest 首次读取时验证、迁入 SQLite 后改名留档。创建编辑及历史导航均在项目写锁内校验调用方提交的 `base_revision_id`，当前版本已变化则拒绝提交。
- `backend/app/api/media_agent.py`、`backend/app/services/media_edit_delivery.py` 与 `backend/app/services/media_export_delivery.py`：项目、导入、版本、撤销/重做、预览、导出和下载接口；确定性编辑和 PNG 导出均通过异步受理/结果接口复用 `WorkflowRun`、事件流、步骤与工具调用，而不是单独维护媒体任务表。修订或复制完成后先以 Pillow 回读验证；编辑任务以 revision task_id 对账，导出任务再登记受控 `media_exports` Artifact。编辑仅能在工具开始前取消，避免“已写入修订却显示已取消”的矛盾。请求只接收 Base64 字节和文件名，拒绝本机路径输入或路径穿越。Pydantic 为每种编辑操作校验参数组合，非法空调色、缺失裁剪参数和超限尺寸返回 `422`；操作缺少或携带错误版本不再静默套用后端最新版本，过期版本由服务层返回 HTTP `409`。
- `backend/scripts/verify_media_workspace.py`：验证新项目不产生活动 JSON manifest、v1 JSON 工作区迁入 SQLite v6 并留档、源图哈希不变、调色 -> 缩放 -> 裁剪 -> 旋转 -> 灰度的版本链、alpha 保留、参数审计、撤销/重做、分支后清空重做、导出文件回读、路径边界和项目重开；矩形蒙版夹具检查二值 PNG 尺寸和像素、修订引用以及选区外透明/选区内 Alpha 不变，并覆盖蒙版撤销重做。栅格图层夹具检查来源修订冻结、目标区域像素合成和来源后续修改不回写旧成品。另注入 SQLite 写入失败，确认新项目目录、未登记导入、未登记修订和未登记导出都会被回收。该夹具只覆盖可捕获异常后的补偿，进程崩溃窗口仍待 HARD-08 验证。
- `backend/scripts/verify_media_workspace_api.py`：通过 FastAPI 验证项目创建、导入、参数化修订、矩形蒙版和栅格图层预览、撤销/重做、导出、下载及非法参数的 `422` 状态码；异步编辑会验证统一任务终态、步骤输出、工具调用、冲突和入队后取消不生成修订，异步 PNG 导出还会验证隐藏绝对路径的 Artifact、工具调用以及取消清理。

- `mediaworkspacedialog.{h,cpp}`、`mediaimagecanvas.{h,cpp}`、`backendclient.{h,cpp}` 与 `mainwindow.cpp`：从“视觉工作室”进入独立 Qt 工作区；通过本机 HTTP API 完成项目/素材/修订/历史导航/预览/导出，客户端不提交绝对路径。裁剪和蒙版用画布拖拽矩形，按实际图片显示区域换算为原图像素，并与可见步进控件双向同步；确定性编辑和 PNG 导出都会先创建 Runtime 任务、轮询已验证终态，再刷新修订链或以 `QSaveFile` 原子落盘。编辑运行期间锁定项目、素材和版本选择，避免异步结果落入已经切换的界面上下文。撤销/重做是带提示的图标按钮，历史版本只允许预览/导出，避免其被错误编辑为后端当前版本。收到版本冲突的 HTTP `409` 后，客户端自动重新拉取项目与修订链，选中最新版本并提示用户重试。
